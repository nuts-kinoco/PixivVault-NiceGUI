# 起動時の共有停止ロックの棚卸し

対象は `fix-busy` の土台 `254b70e` と今回の差分。Busy はロック競合を示し、停止記録の内容は取得できていない。実機で観測された `blocked=0` はプロファイル側の記録で、共有所有者や選択履歴のロックが空いていた証拠にはならない。

| 経路 | 一時的か恒久か | 修正前の扱い | 今回の扱い |
|---|---|---|---|
| 共有所有者がまだないときの `.pixivvault-user-stop-startup.lock` のバイトロック | 別プロセスが保持中なら一時的 | `_FileLock` の `OSError` を即 Busy。構築中のファイルに空の状態が見えることがあった | 完成した初期バイトを一括公開。実ロック競合に限り再試行。取得後に所有者の有無を再照合 |
| 同ロックの空・不正な初期バイト、開いた後の同一性変更 (`MigrationRejected`) | 修復が必要 | 起動用ロックでは Busy。選択履歴では保存エラー | どちらも保存エラー。記録を保持して再試行しない |
| 同ロックのパス・親ディレクトリ・権限・入出力の異常 | 修復が必要 | 親作成や `_FileLock` の `OSError` は Busy。リンク等のエラーは別 | 保存エラー。Windows は非ブロッキングロック操作の `ERROR_LOCK_VIOLATION` だけを競合として扱う |
| 選択済み旧画像・小説・うごいら履歴の `.pixivvault-network-stop.sqlite3.lock` | 旧書き手が保持中なら一時的 | 履歴検査中に `_FileLock` の `OSError` を即 Busy。SQLite sidecar が先に見えた場合は保存エラー | 競合だけ再試行。ロック取得後に sidecar の残存、所有マーカー、同一性、停止記録を検査。DB/ロックのいずれもない場合も sidecar の有無を確認 |
| 選択履歴の DB/ロック欠落、同一性・マーカー不一致、排他下で残る SQLite sidecar | 修復が必要 | 保存エラー。履歴から通信を許可しない | 同じ。再作成・上書き・自動回復は行わない |
| `ManagedNetworkStopGate._exclusive` のプロセス内 RLock と DB に付随するバイトロック | 他の処理が保持中なら一時的 | RLock は 0.5 秒で Busy。OS バイトロックは即 Busy。共有所有者を開く処理やプロファイル STOP の読み取りにも伝播 | 共有起動中の該当操作を同じ 8 秒の予算に入れる。通常の GET や利用中の処理に新たな再試行は加えない |
| 初回所有者の公開前に使用する選択履歴ロック | 履歴書き手が保持中なら一時的 | 起動用アンカーを作る前に Busy で戻る | アンカーの書き込み前に同じ予算で再試行。正式移行の形跡は待機前とアンカー書き込み直前に確認 |
| 初回のアンカー作成後、ステージのゲート初期化や STOP 記録でロック予算を消費 | 未完の所有記録を検証する必要あり | Busy または保存エラーのまま記録を残す | ロック取得を有限時間で試す。予算を使い切ったら未完の保存状態として記録を保持 |
| 既存所有者を開いた後、画面登録の選択履歴再検査で競合 | 一時的 | `register_pages` から Busy、オフライン設定画面で再起動案内 | 起動と共有する締切まで競合を再試行。共有ゲートを確認する入口がある場合には同じ「再確認」を表示 |
| 画面登録の読者作成がプロファイル STOP を共有ゲートに集約するときの競合 | 一時的 | 未公開の読者を閉じて Busy で戻る | 未公開の読者を閉じて同じ締切までローカルの生成と集約を試す。STOP を保持し、GET は発行しない |
| 共有起動より前のプロファイル停止スコープの構築や保存先の結合 | 根拠はエラー型による | Busy または保存エラーでオフライン。所有者不明は移行案内 | 共有起動を再実行してもプロファイルの所有を証明できないため、従来の復旧経路 |
| 停止済み (`ManagedNetworkStopped`)、前回取得の結果不明 (`SharedGetOutcomeUncertain`)、既存所有者の消失 (`SharedStopOwnerAbsent` や保存エラー) | STOP・確認要・修復要 | 停止か復旧に分岐。所有者が最初から存在しない場合のみ初期化を検討 | Busy 再試行の対象外。設定画面の再確認では STOP と送信中記録を GET と同じ排他内で確認し、記録を変更せず状態を案内 |
| 明示的な正式移行の `source_busy` (`MigrationRejected`)・移行ロック・移行記録 | `source_busy` は一時的。その他の破損・食い違いは修復または再調査が必要 | 移行画面で中止、手動確認。通常起動が移行を自動実行する入口はない | 既存の移行操作を維持。通常起動は移行の記録を検出した場合に初期化を停止 |

## Windows の再現と実機事象の区別

- 隔離した子プロセスに起動用ロックを持たせ、親が実ロック競合を観測した後に、その子だけを強制終了した。土台では Busy で即終了し、修正候補では保持が消えた後に初回起動に進んだ。ロックファイルは `0` のまま残る。単にファイルが残っていることはロック保持を意味しない。
- 別スレッドに選択履歴ロックを持たせ、SQLite トランザクションで実際に一時ジャーナルを作成した。ジャーナルを見ただけでは実行中の書き手と破損を区別できない。ロールバックと解放後の起動で停止コード 429 と旧 DB のバイト列を保持した。
- 07:20 に保持していたプロセス、ハンドルの解放時刻、実際に競合したロックまでは未確認。起動用ロックは共有所有者の既存検査で `SharedStopOwnerAbsent` が出た場合に限って使われる。共有所有者が有効だった場合は、共有ゲート自身や、選択履歴・プロファイルゲートでの競合もあり得る。09:20 の復帰は一時競合と整合するが、原因を確定しない。
- 正式移行は別の排他で動く。今回追加した待機後に移行の形跡を再確認する。従来からの、移行開始とアンカー公開の間の並行操作までを直列化する変更はこの候補の範囲外。
