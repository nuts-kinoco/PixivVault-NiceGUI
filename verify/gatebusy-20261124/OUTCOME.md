対象は `gatebusy-20261124`、基点 `052ecdef51ccec684df42cf116608e123a6b78da`。検証候補はこの文書を含むコミット。

## 原受入

隔離ブラウザーで、基点の固定通知 3 件を再現し、修正後に 0 件、取得経路 4 件と合成ランキング応答の表示を確認した。CoS R8 の実機 A2・G2 は監督確認待ち。複製では実機報告の「確認に使える取得経路がない」表示と借用 ON の組合せは再現していない。

## 原因と再現

1. `S:\Projects\PV-DEV-20261117\backup\realprofile-20261124-r10\profile-native` から、プロファイル設定 DB・マーカーとローカルゲート DB・ロック標識を `S:\Work\_tmp\PV\gatebusy\profile-native` に複製。バックアップのプロファイルゲートは `blocked=0 / status=None / revision=0`。バックアップの選択済み画像・小説・うごイラ保存先に旧ゲート DB はなかった。
2. 設定に実機への絶対パスが残っていたため、複製内の参照だけを合成 Cookie と新規の隔離保存先に変更。既存の `isolated_test_workspace` で共有ゲートも S: 内に作成。外向き接続を拒否し、最下層の HTTP トランスポートのみ合成応答へ置換した。
3. 製品 CLI は `--profile-root` 単独の非 Native 起動を引数検証で拒否する。診断ランチャーで `--native` の引数検証を通し、返った設定の `native` だけを False にして `bootstrap.main` をポート 22391 で実行。隔離した Playwright Chromium（Edge）からヘッダーを読んだ。実機 22386 は開始・終了時とも同じリスナーで、接続・再起動なし。共有ゲートを分離したため、実機との同一ゲート競合は未測定。
4. 合成ホーム GET をゲート内で 4.8 秒保留して初回画面を開く。基点では ASGI の学習ウォームアップが取得中に、初回画面の認証も GET の入場を試みた。両方の経路で `managed gate thread lock unavailable` を観測した。通常ヘッダーの 3 件は、学習取得の実拒否 1 件と、監視がローカル・共有のロック観測から作った 2 件。後続の `changed` → `open` 観測でゲートが開いても 3 件残った。起動時のオフライン復旧画面には入らず、取得リーダー 4 件と明示再確認ボタンが存在した。
5. 取得経路が無い表示の生成条件は回帰試験で再現した。共有だけの取得経路を持つポリシーにローカルの競合・変動観測を渡すと、基点は再確認経路に結び付けられない固定通知を作る。実機の表示がこの経路だったかは未確定。

## 修正

- `native_startup.py` の初回ヘッダー認証は、同じアプリで先に始まった学習ウォームアップの完了を待つ。待機中にサービス終了が始まった場合は認証を始めない。
- `request_policy.py` は、監視の Busy や指紋変動だけで新しい固定通知を作らない。観測の不整合は引き続き明示再確認の証明を無効にできる。実際に拒否された取得、永続 STOP、保存異常、結果不明は既存の通知・ゲート判定を通る。既存の固定通知の解除には明示再確認が必要。
