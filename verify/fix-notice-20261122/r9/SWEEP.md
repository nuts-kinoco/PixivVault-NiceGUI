# 第9回　待機、取得入口、最終確認の棚卸し

基点 `456cf0e6`。Sol 再検証の全文を読了。停止確認は実送信前だけに適用する。送信済みの応答を打ち切りと取り違えず、取得自体の許可は既存のゲートが決める。

## M1　待機と送信

| 待機・分岐 | 429 停止の確認位置 | 永続 STOP、結果不明、所有の確認 |
| --- | --- | --- |
| 発行間隔の予約、対話側を優先するための待機 | 発行枠に入る前、各待機の後、発行枠から読取入口に戻った時点 | 発行枠の後、実取得のゲートが照合 |
| 通常再試行のバックオフ（429 と通信障害） | 待機明けの各試行入口と送信直前 | 新しい試行でもゲートを通る |
| プール切断後の1回限りの新しい接続 | 再試行入口と実送信直前 | 新しい読み取りの開始からゲートを通る |
| 保存済み参照の確認、コーディネータのロック、所有／旧履歴の確認、ゲートの RLock・ファイルロック、SQLite 確認 | 読み取り入口に戻った時点と、取得ゲートがすべて通った直後 | RLock／ファイルロックを保持して既存の所有・STOP・結果不明を照合 |
| 既存 HTTPS 接続のプール確保、DNS／TCP／TLS（標準 HTTPS） | プールに入る前の境界と、接続が使えるようになり HTTP データを渡す直前 | 取得側のゲートは送信まで保持 |
| ジョブ取消、期限切れ | 既存の取消・期限チェックを維持 | 送信拒否 |

別操作による429の送信前拒否には内部の型を使う。取得中の実際の HTTP 応答として永続 STOP を誤記録せず、すでに作った当該 GET の intent を既存の終了経路で片付ける。呼出元の HTTP 429 と既存の「送信前に停止」の表示は維持する。

## M2　記録より前の早期拒否

| 入口 | 既存の早期拒否 | 固定通知にする対象 |
| --- | --- | --- |
| 公開 GET の `_ensure_open` 呼出（画像、識別、ブックマーク、作者一覧、作品／小説情報、ページ一覧等） | 明示 close、所有プール終了確認不能 | 終了確認不能をこの共通境界で記録 |
| 公開メソッドから `_json`／`_get` へ進む入口（ランキング等） | `request_scope` の `_ensure_open` がポリシーの試行記録より先に失敗 | 同じ固定通知と監視起動 |
| 取消・期限、入力／宛先不正、認証や設定の拒否、すでに確定した429 | 既存の例外と終了 | これらをプール終了異常に変換しない |
| 初回試行のコーディネータ・ゲート・HTTPS、試行中／応答後の `_ensure_open` | 記録内の既存の拒否 | 同じ固定通知を重複させず保持 |

## L1　最終確認

| 段階 | 内容 |
| --- | --- |
| first／read／last／confirm | ファイル指紋に、SQL を発行しない共用 R/W 接続の開閉成否を含める。close の失敗は DB／ロックの内容変更がなくても検出する |
| verify／verify_fingerprint | 競合や異常後の診断でファイル指紋と R/W 開閉を照合 |
| seal | 全フック後の最後の指紋取得でも共用 R/W 開閉を実行。新規終了異常は unverified として通知を保持 |
| 読み取り済みの STOP／結果不明 | 後続の終了異常と併記。既存の2回連続確認による解消を維持 |

R/W 開閉は既存ファイルだけを対象にし、SQL・復旧・新規作成・バイトロックは行わない。

## 回帰試験の対応

| 系列 | 試験条件 |
| --- | --- |
| M1・発行枠 | 同じポリシー／発行枠を持つ2操作。普通の429上限に加え、上限1と3で一度限りの共有ロック close 異常を併発 |
| M1・ゲートと再試行 | ロック待ち、プール切断後の新しい接続のゲート待ち、通常の再試行待機。期限・取消を維持し、永続 STOP と結果不明を設定した対照も確認 |
| M1・標準 HTTPS | 接続成立中に別操作の429停止を確定させる。HTTP バイトを渡す前に拒否することを確認 |
| M2 | 期限切れの idle 所有者の cleanup に OSError。画像とランキングの公開入口を local／shared で確認 |
| L1 | first／read／last／confirm の全対象の前後に、ローカル／共有の SQLite close 異常を再発。診断 verify／verify_fingerprint の前後にも反対側の SQLite 異常を注入。計40組 |

429の確認はアプリ内の最終送信境界で行う。確認を通過した送信は実行中として扱い、ソケット呼出し中にポリシーの状態ロックを保持しない。ネットワークへのバイト引渡しとの不可分性や、最終確認後の割り込みは別の性質であり、実測は表の待機境界で行った。SQLite の一時的な失敗が再確認で回復した場合は観測競合として既存通知の解消を保留する。
