# 第15回 取得停止通知の検証

候補は `fix-notice` の `4660a2ec`。ユーザーが列挙した A–E を、明示確認版の範囲で修正した。原受入には監督側の独立検証と R8 実機表示が残る。 [棚卸し](SWEEP.md) [候補と試験所有](candidate-state.txt)

| 指摘 | 修正と回帰試験 |
| --- | --- |
| A 拒否を記録する前の解除 | OS 失敗を捕捉した地点で、分類・型付き変換に先行して記録する。Win32 の応答と Python 側捕捉の間は、同じ物理ゲートの I/O が進行中なら解除を保留する。進行中件数と拒否世代を一つのスナップショットで比較する。同一ポリシーと別ポリシーで再現した |
| A ロック手前の検査漏れ | ライブの物理キーを共有オーナー、選択 Cookie、旧履歴へ束縛した。新しい GET、Native、フォロー同期、公開 CDN、設定後の Cookie 更新、明示書込みで共通の拒否記録を使う |
| B 正常な再確認が結果不明を作る | 番兵の処理・ロック取得に先行して開始を登録し、終了も単調な世代に記録。観測の開始・終了に重なった物理ゲートのサンプルを捨てる。再確認の前後・途中・入れ子で番兵が残らず、誤通知を新設しなかった |
| C 別対象の不整合を取りこぼす | 各対象のフィンガープリントと確定読取りを個別に評価する。共有側だけを捨てる間も、ローカル側の不整合は同じ周期に表示した |
| D 後続の成功による相殺 | 先行リーダーのみでロック拒否・close・番兵除去異常を起こすと、第14回候補では後続リーダーの成功で解除された。修正後は、全候補が成功するまで解除せず、停止・保存異常と再確認不能な終了異常を記録した |
| E 両所有元が未設定の場合の重複 | 初回のローカル拒否と、同じ理由・同じ対象の観測を1件にまとめた。共有側の不足は個別に表示した |

再確認が開始する前に完了した観測は保持する。その後も別の実競合が続く場合は、重ならない次の周期で観測する。所有関係を検証できていない経路に架空の物理 ID は割り当てない。取得の許可判定、終端 429 の送信前チェック、成功 GET・期限経過で固定通知を保持する仕様を維持した。
