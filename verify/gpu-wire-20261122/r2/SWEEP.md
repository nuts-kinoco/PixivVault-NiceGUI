# 共有GPUリース経路の棚卸し

修正前の確認対象は `f73baf5` と共有 v2 の読み取り。v2 の `--wait 1` は混雑時に 20 秒 sleep し、ファイルロックと子コマンドにも別の待ち時間がある。`--pid` の生存性と期限で有効性を判定し、release はトークンを原子的に照合する。

| 経路 | 旧挙動と確認点 | 修正後に確認する条件 |
| --- | --- | --- |
| 正常取得 | v2 内部の待機を指定 | 6 GiB・30 分・単発試行。実行開始前に有効期限を検査 |
| 空き待ち／EMA保持 | v2 の sleep 中に Event が届かない | Pythonの Event 待機で即座に解除。CUDAもCPUも開始しない |
| 取得直後と停止の競合 | 応答が届けば finally で解放 | トークンを得たら、キャンセルの検査前に解放処理を確立 |
| 取得例外・タイムアウト | 書込み後／応答前に強制終了するとアプリ PID のリースが孤立 | 子コマンドの制限時間を停止予算内に収め、専用の所有 PID を終了して孤立した記録を無効化 |
| 期限接近／ローカル GPU 待ち | 外側の 60 秒チェック後に境界を越えると GPU 失敗として世代を失効 | VRAM を解放して旧リースを返し、同じ項目で取り直す。停止・purge を再照合 |
| 推論例外 | ExitStack でセッションを先に閉じる | 例外でもトークン付き解放を一度試みる |
| 解放・解放失敗 | 35 秒の待機。既存の後継トークンは拒否される | 停止予算内。後継リースは維持。返答不能は未確認として伝え、専用 PID は終了 |
| 共有停止・アプリ終了 | cancel 後も v2 sleep が残り得る | 待機を解除し、他の停止信号を先に送り、両方の終了失敗を保つ |
| 強制終了・期限切れ | アプリ終了で PID 無効。生きたままの取得タイムアウトは最大30分 | 所有 PID の stdin をアプリだけが保持し、強制終了でも EOF で終了。 v2 のロック stale 判定は従来どおり |
| 実 GPU | v2 と ORT は実機で動作未確認 | 今回は偽ヘルパー・偽推論のみ。実機を起動しない |

## 修正候補の境界

- `--wait 0` を使用。各ヘルパー呼出しは8秒、試行間の待機は2秒で Event に反応する。取得タイムアウト時は専用 PID を終了させてから新規 PID で再試行する。返答が届いた取得は停止との競合でもトークンを一度だけ返す。解放の打切りは未確認エラーになる。
- v2 が失効済みトークンを残す場合でも、後継のトークンは release の原子的照合で保つ。通常の期限接近は CUDA セッションを閉じ、旧リースを返して同じ画像で取り直す。ローカル調停待ち中と CUDA の load・run の各境界で期限を照合する。
- ロック内部でヘルパーが打ち切られると v2 のロックは書込み時刻から30秒超まで残り得る。8秒を超えるプローブが繰り返されると PV は待機を続ける。Windows の子コマンドに対する一次プロセスの終了伝播は v2 の契約外。v2 の PID 照会自体が失敗した場合は保守的に生存扱いし、契約どおり期限が最終手段になる。
- 既に実行中の不可分な CUDA 呼出しは協調停止の対象。実機上の停止時間や外部ヘルパーの子コマンド残存は今回の偽ヘルパー試験では測っていない。
