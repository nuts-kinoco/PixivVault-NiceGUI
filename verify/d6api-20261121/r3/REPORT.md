## 指摘への対応

| 指摘 | 実装と確認 |
| --- | --- |
| M1 | 再利用 GET が HTTP 応答の先頭バイトより前に EOF・接続切断となった場合に、未消費の試行枠で新規 TLS の GET を1回だけ実行する。再送は同じ期限で、宛先・Cookie・アカウント・送信前の入場制御と両ゲートを再確認する。再送禁止スコープ、設定1回、別の要求ですでに共有429上限に達した場合は再送を止める。新規接続で応答前に失敗した場合は通常の設定済みリトライを維持し、応答が始まった後の通信中断は両接続で打ち切る。 |
| M1 ゲート | 1回目の正常に分類できた無応答切断で既存ゲートの in-flight 印が片付き、再送時に新規の入場と印が付くことを実ソケットで確認した。間に共有 STOP または成否不明を作る試験では追加送信0で、成否不明の印を保持した。 |
| L1 | `close()` はアイドルの破棄待ちに入る前に閉鎖を公開し、進行中のソケットを停止する。進行中とアイドルの各 TLS ソケットを作り、アイドル破棄を待たせて確認した。 |
| L2 | 再利用済みの TLS では同じ SSLContext を使う。新規接続のときだけ、生成ロック内の最新 epoch でキャッシュを得る。旧接続を借りた直後に別クライアントが新 epoch を公開しても、SSLContext の余分な再生成がないことを確認した。 |
| L3 | 文書化。Windows はフェンスの shutdown が待機中の読み取りを即時に解除しない場合がある。ヘッダーを少しずつ送る応答、または同一 `read1()` 内でチャンク行・本文・トレーラーを複数回受信する応答では、直前に設定したソケットタイムアウトが残り、ワーカーとゲートのロック解放が絶対期限より遅れる場合がある。 |
| L4 | 2層ゲートと再試行設定ありの401/403、通常429の既存制御、接続回復時の429即停止を試験。タイマーを動かさない状態の期限切れと TCP RST を借り出し時に破棄することを実ソケットで確認した。既存のクローズ試験もサーバー側の EOF で観測するようにした。 |

通常の明示429は既存の B3 の待機・回数に従う。無応答切断からの回復 GET で返る429は両ゲートで即停止する。回復 GET の応答・失敗はそのまま呼び出しに返し、回復後の追加試行を行わない。 [重点回帰](green-final.log)
