## 実利用差の解釈

基準の NiceGUI は各 GET で `ssl.create_default_context()`、DNS スレッド、新規 TCP/TLS、`Accept-Encoding: identity` を使っていた。元 Flet の `PixivClient.get_ranking` は `_request_with_retry` で同一 `requests.Session` の `get` を使い、圧縮を要求する Requests の既定ヘッダーを維持している。 [Flet クライアント](S:/Projects/PixivVault/pixiv_client.py)

Flet 計測環境に入っている Requests 2.32.5 と urllib3 2.6.2 で、既定の gzip 要求とアダプターの接続プールをローカルで確認した。

既存の10ペアでの API 中央値 / p95 は Flet 59.55 / 69.14 ms、NiceGUI 212.61 / 270.02 ms。ペア内差の中央値は152.27 ms。既定コンテキスト生成のローカル中央値は約21 ms。TLS 1.3 の通常の新規接続で TCP と TLS が各1往復を要すると仮定すると、約60 ms の応答時間を上限の目安にして接続だけで最大約120 ms の規模になる。旧実測には DNS、TCP、TLS、転送量の独立標本がなく、圧縮の実回線寄与は分離できない。計測待ちの中央値は Flet 72.04 ms、NiceGUI 218.07 ms。台帳による応答終了後の待ちを含み、表の API 区間とは別。 [旧実測](S:/Work/_tmp/PV/d6real/round3-live01/ranking-summary.json) [旧監査](S:/Work/_tmp/PV/d6real/round3-audit.json)

## 安全境界

- SSLContext の初回生成を直列化し、既定の CA・ホスト名・証明書検証設定を再利用する。
- アイドル接続は API オリジン、所有クライアントごとに最大1本。継続利用する TLS ソケットは同じ SocketFence に登録したまま、各試行で期限を更新する。取得停止ゲートは毎回、接続を借りる前に判定する。Cookie は従来どおり各 GET に組み立てる。
- 完了・フレーミングを確認した 200 だけをプールへ返す。タイムアウト、途中切断、HTTP 異常、圧縮異常の接続は破棄する。401/403/429 はヘッダー解析に失敗しても取得停止ゲートへ伝える。ソケット層からのリプレイはない。
- gzip は API JSON のみ。受信と展開をそれぞれ `JSON_LIMIT` で制限し、破損、途中で切れた gzip と余剰データを拒否する。DNS キャッシュは追加しない。画像・ZIP・POST の接続再利用は対象外。
- `close()` はアイドルソケットを即時に破棄し、使用中のソケットは既存フェンスで shutdown する。Windows の待機中読み取りでは shutdown を観測してからワーカー終了まで最長で既存の要求期限を要し得る。

## 検証と逸脱

- 基準で追加テストを先に実行し、17件の失敗を確認した。実装後、接続を閉じる応答の確認も追加した。関連73件が合格し、うち18件が今回の TLS 回帰。通信棚卸しは302箇所、未分類0。 [Red](red.log) [重点試験](focused-final.log) [通信棚卸し](network.json)
- 初回全体試験は指定した短い `--basetemp` が長パス試験の前提を満たさず、担当が起動したプロセスツリーだけを終了した。既定の pytest 一時パスで同じ試験が合格したため、一時ディレクトリの起点を S: に維持して全体を再実行した。 [初回ログ](full01.log) [長パスの再確認](long-path-probe.log)
- 全体 pytest は3,972件合格、失敗・エラー0、Windows のシンボリックリンク権限で3件スキップ、DPAPI 3件除外。26分45秒。要求されたネットワークガードと S: の TEMP/TMP を使用した。 [全体試験](full02.log)
- 使用中 TLS の shutdown 成功後、Windows の読み取りワーカーが2秒以内に終了するという初期テストの仮定は成立しなかった。既存契約どおりの即時 shutdown と絶対期限内の終了を確認した。アイドル時の即時破棄は別に確認済み。 [初期の観測](close02.log) [重点試験](focused-final.log)
- 取得停止ゲート、認証・Cookie、並行処理は本人が手配する独立検証の対象。記録した起動 PID の残存は0。 [残存確認](process-check.json)

## 実通信への引継ぎ
