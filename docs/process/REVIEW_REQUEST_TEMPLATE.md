# 独立検証の依頼テンプレート（PV、2026-11-19 採用）

検証依頼（Sol の `--role review` など）の冒頭に、次の項目を必ず入れる。空欄にせず、無ければ「なし」と書く。

## 0. 対象
- worktree と HEAD（`git log -1`）、差分の範囲（`git diff <base>...HEAD`）。読み取り専用、ファイルは変更しない。
- 前回の結果ファイル（あれば）と、その指摘のうち今回直した点。

## 1. 受入の基準（最初に固定する）
- **採用済みの原受入**: 台帳の行（FL-xxx）と、元アプリの該当コード（file:line）。
- **変更前に保証していた挙動**: 変更前の移植版（`git show pv-dev-baseline:<path>`）が守っていた保証。
- **移植先で必要な差分とその理由**: 元と違う実装にした点と、現在の要件で元の方式を再利用できない理由、追加する保証。元の方式を変える場合は、必ずここに書く（書けないなら元の方式を使う）。
- **守るべき不変条件**: 保存・削除・復旧・取得停止ゲート・認証・並行処理について、数行で。
- **対象範囲の前提（必ず書く）**: 既定は「ファイルを外から変更する操作や、検証と使用の間に内部状態を入れ替える試験用の操作は対象外」（アプリが自分で作るデータの整合・クラッシュ・並行保存・通常の操作の競合は対象）。対象に含める操作がある場合は、ここに理由つきで列挙する。列挙のない不正な操作の再現は「所見」に分類する。
- **用語の注意（運用の記録）**: OpenAI 側の安全フィルターで検証が判定を出さずに止まる例が 2 回あった（「脅威モデル」「改変」「競合差し替え」「攻撃」などの語を含む依頼）。依頼文は「対象範囲の前提」「変更」「入れ替え」「不正な操作」などの語で書く。止まった場合は判定が出ていないので、言い換えて 1 回だけ再送する（重複送信ではない）。

## 2. 指摘の分類（報告に必ず付けさせる）
各指摘に、次のどれかと根拠を付ける。
- **原受入違反**: 現在の原受入または必要な保証に違反する（元にも存在した欠陥であっても、現在の原受入に違反するなら未達）。
- **今回の変更による悪化**: 変更前の移植版または元より悪くなった。
- **追加の改善提案（所見）**: 現在の原受入や必要な保証に含まれない追加要求。受入には影響しない。
重大度は「データ喪失／正常な保管庫が開けない／取得停止ゲート迂回」を high 以上とする。

## 3. 既知の限界（総監督が受け入れたもの）
受け入れた限界は、根拠（元と同じ性質・実害のない一時的な状態など）つきで列挙する。限界を増やす場合は、受入の基準を緩めていないか自問する。

## 4. 証拠の再利用（運用 C）
- Terra／実装担当の全体テスト・スモークは、対象 hash・試験範囲・依存関係・設定が一致するなら再利用する。取り直さない。
- 追加実行は、指摘の再現・変更の影響範囲・未証明の重要条件に絞る。同じ全体試験を独立性のためだけに重ねない。

## 5. 報告の形式
受入可否。指摘は「重大度 | 分類 | file:line | 症状 | 再現」、所見は別表。レビューの呼出回数を実装の失敗回数として数えない。

## 6. 網羅先行（欠陥の型）
自由探索ではなく、次の順で報告させる。(1) 対象の不変条件ごとに、**その不変条件を破り得る全ての箇所**（消費箇所・書込み箇所・再照合の結果を使う箇所）を grep で列挙する。(2) 各箇所について、不変条件を満たす／破る／判別不能を判定する。(3) 破る箇所のうち再現できるものを再現する。指摘には「欠陥の型」（既存の型の名前、または新しい型）を付ける。同じ型が前回までにあれば「再発」と明記する。
