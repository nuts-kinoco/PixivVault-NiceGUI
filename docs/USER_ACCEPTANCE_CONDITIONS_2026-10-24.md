## Additional user conditions

The migration is not accepted solely because the Python test count is green. Acceptance must also cover actual user journeys and establish that the app is responsive, visually coherent, and consistent:

1. **End-to-end user journeys** — exercise the complete user-visible flow through the real app shell, including author selection/differential download, enqueue, queue completion/history, library refresh/author/work navigation, multi-page viewer and focus restoration, scheduler settings/dispatch/history, explicit metadata-ledger open/configure/inspect, app restart, and restore/normal exit. Use synthetic fixtures for deterministic automation; use the existing explicit-cookie read-only path only for bounded live Pixiv validation.
2. **Responsiveness** — measure input/click → observable completion, not just API return or a test's eventual success. Keep cold startup/navigation, local setting/state actions, synthetic network/queue work, and warm viewer page turns separate. Report p50/p95/max and sample counts, record timeouts/failures rather than dropping them. Do not infer whole-app speed from the viewer benchmark alone.
3. **Visual coherence** — inspect actual Edge and Windows native screenshots at 1280×720 and 1920×1080, including initial display, tab navigation, download/queue, library/viewer, metadata settings and restart/restore. Check readable typography, spacing/alignment, hierarchy, overflow/clipping, empty/error states, focus restoration, and stable geometry. Retain the screenshots and their source SHA metadata; do not use the old baseline screenshots as current acceptance.
4. **Comparison discipline** — reuse `docs/MATCHED_VIEWER_BENCHMARK_2026-10-22.md` only for its exact warm, synthetic, 175%-DPI, 60-transition viewer conditions. Its Flet p95 250.330 ms vs NiceGUI 122.386 ms is a scoped observation, not an overall product-performance guarantee. The 32.2% higher private bytes observed on the NiceGUI side is a trade-off to retain in reports, not conceal.
5. **Raise concerns instead of blindly copying** — when a source behavior or UX is awkward, report the concrete user impact, evidence, and a minimal recommendation. Do not implement large scope changes without a separate decision; ordinary correctness/usability fixes can be made within the already authorized migration scope and must receive review/tests.
6. **Merge gate** — independent code review, full regression suite, real user-journey acceptance, performance measurements, visual inspection, clean exact-head CI (Windows, Ubuntu, Chromium), and applicable native/restart/data-preservation gates must all pass before merging. A green unit suite or invited reviewer alone is not approval.

## Known limits / concerns to report, not hide

- The current acceptance fixture is deterministic and synthetic. It does not by itself establish performance at large real library sizes, cold first launch with real data, a second PC, or all Windows DPI scaling factors.
- The application uses a desktop-wide shell and a very dark palette. Inspect real-size screenshots for readability and unused space at ultrawide sizes; do not declare visual quality from CSS/test counts alone.
- The explicit metadata GET is one work per user action; it is not an automatic backlog processor. During an in-flight bounded GET, a new download enqueue can wait until the GET drains. This is a deliberate serialized safety trade-off and should be assessed for user impact, not silently described as instant preemption.
