# 旧 failed_queue → 新管理キューへの限定再試行

## 明示opt-inのみ

次の3つをすべて指定する。指定がない従来起動・旧DB読取画面は**変更しない**。

```text
--pixiv-cookie-file <既存の認証Cookieの絶対パス>
--pixiv-download-root <元PixivVaultと独立した専用管理先>
--failed-queue-readonly-db <静止した旧failed_queueの単一SQLiteコピー>
```

旧アプリDB原本を指定せず、原アプリを停止した状態でSQLiteの完全なオフラインコピーを別ディレクトリに作成すること。`-wal/-shm/-journal`が併存する不完全なコピーは拒否する。専用読取処理はSQLite `mode=ro&immutable=1` / `query_only=ON` のみで、SQLite側carve-outの書込や元DB移行を実施しない。

さらに起動時に静的DBコピーのサイズ・更新時刻・ファイルID・全内容SHA-256を固定し、一覧読込・受理直前のたびに照合する。**改変があれば投入を停止し、コピーを取り直す**。これにより受入途中のコピー差し替えを検出するが、利用者が選んだ入力が「本当に原本とは別の正しく完結した複製か」までは自動証明できない。ファイルが原本のままの状態で渡されていても操作で修正はしないが、その運用を受入済みとは扱わない。

## 接続済み操作

- 失敗リストの各行「再試行」と、検索・カテゴリで絞り込んだ結果の「対応作品最大50件を再投入」。現在表示中の1ページのみではなく、フィルタ全体から選ぶ。
- `work_type=illust` / `manga` のみ。小説・うごイラ・不正ID・不正作者IDはUIで無効化し、サーバーでも拒否。
- 受理直前に**静的旧DBコピーの全件**を再読し、選択行7項目の一致を確認。その後、許可されたPixiv GETで作品の実ID・作者・作品形式・ページ数を照合。許可された通常イラスト・漫画のみ既存の管理SQLiteジョブ、receipt、共有ライブラリへ接続。
- 1つの明示クリックは固定operation IDで二重受付を防ぎ、同じ行を終端ジョブ（成功・エラー・停止）後に**新たに押した場合だけ**別operation IDとして再投入する。以前の終端結果を新しい成功と偽って表示しない。画面の一時ピンは受理・拒否の後に即解放するため、50件ずつ繰り返しても128件のowner候補上限に蓄積しない。
- 受理結果が確定しなかったI/O例外では同じoperation IDを保持して安全に再照合する。一方、そのIDで永続化されたintentと更新された作品メタデータが衝突した場合、旧意図を上書きせず次の明示クリック用IDへ切り替える。旧受理intentは履歴として残す。
- 既存の managed JobService に停止・一時停止・再開・エラー再試行・再起動復旧を委譲。古い失敗リストの行・回数・日時・エラー理由・元画像は一切変更・削除しない。
- UIはclientごとにowner/検索/選択/epochを分離。失効したページ・タブの遅いGET応答は新たなキュー投入として受理しない。受理済みSQLiteジョブはclient closeでもapp所有で継続する。
- 複数件の再投入は最大50件。1件でもGET・検証・SQLite確定に失敗したら残りを投入しない。既に受理した作品は戻さず管理キューに残す。ユーザーには件数を示し秘密のレスポンス・実ID・URL・Cookieをログに表示しない。

## 受入境界

- 原版 `gui.py:4199-4309` は単一作品・フィルタ全件再試行に加え、成功時に旧DB失敗行を消す。NiceGUI側は**独立管理保存かつ旧DB原本絶対不変**が上位制約なので、失敗行の削除を明示的に実装していない。したがって「完全原版同等」をこのマイルストーンで認定しない。
- 旧保存先への直接修復・ZIP命名更新、失敗原因に応じたnovel/ugoira再試行は未対応。これらを既存管理ジョブへ偽装投入しない。
- 実Cookieの限定実画像ダウンロードはこのブラウザ試験の一部ではない。ブラウザ受入は架空Pixiv GETダブルと架空SQLiteだけで行い、原本のスクリーンショットや取得本文を保存しない。
- 静的DBコピーの全体SHA-256を一覧読取前後と各受付前後に計算するため、コピーが上限128MiB近くあると50件の一括投入はI/O律速になり得る。現時点でその最大条件のp95/メモリ実測はない。未測定条件の速度向上やパフォーマンス改善率は主張しない。
