背景: 5 つの UI 修正枝と取得停止通知の修正を統合した候補。前回の独立レビュー（別の AI）が統合不可（High 2・Medium 5）と判定し、その対応が入った第 3 回。前回（第 2 回、別 AI の再レビュー、保留 Medium 4）の指摘: (1) ヘッダー通知を閉じたとき復帰処理が .pv-header 内だけを探索し、メイン画面の有効な起点が除外される (2) 取得通知が 4→3 件に減ると、フォーカス中の「明細」ボタンが復帰処理なしで消える (3) 通常の完了通知と待機のカウントダウンが role=alert (4) 試験の walk_focus が同じ 1 要素に留まっても通る／小説・うごイラが dialog.open() 直呼び。第 3 回はこれらを、フォーカス復帰の共通部品と role の対応表で構造的に直した。それ以前の指摘: (H1) 設定ダイアログの初期フォーカスが見出し（tabindex=-1）のとき Shift+Tab で背景へ抜ける (H2) 取得停止通知の「閉じる」を押した後フォーカスが失われる (M) 生の ui.notify の取りこぼし 7 箇所／他のダイアログにフォーカストラップ未適用／重要停止の通知枠からの押し出し／非モーダルの復帰先検証がない／試験が実装の写し。

見てほしい点（コードを読んで、根拠つきで）:
1. 前回の H1・H2・Medium が本当に直っているか（再現シナリオごとに、該当コードと試験を読む）。
2. ダイアログのフォーカス管理の共通部品（27 入口）: 取りこぼし、Tab 順の誤り、フォーカス喪失、手書きの重複の残り、JS の境界条件（stops の外にフォーカスがあるとき、非表示・無効の要素、複数ダイアログの入れ子、閉じた後の復帰先が消えている場合）。
3. notify_action への統一: 取りこぼし、role（alert／status）の妥当性、data-testid の重複。
4. 試験: 実装の写しになっていないか、実ブラウザーで検証すべきものを単体で済ませていないか。
5. 取得停止ゲート・通信コードに変更がないこと（managed_network_stop_*、request_policy の送信制御、pixiv_*client）。※ request_status_view の通知の「消える条件」には別途再設計が進行中の既知の穴 3 件（共有ロックの書き込み拒否、同一ポーリング内の再発、別ゲートの確認済み引継ぎ）があり、対象外。
6. 新しい欠陥（退行・競合・例外・アクセシビリティ）。
