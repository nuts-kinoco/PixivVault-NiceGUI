背景: アプリには「取得停止ゲート」があります。Pixiv への GET が 401/403/429 になったり、結果が分からない（通信結果不明）状態になったりしたら、通信を止めて固定の通知（未解消のあいだ消えない）を出し、原因が解消したと確認できたときだけ通知を消します。ゲートの取得側（実際に GET を許可するか判断する側）と、通知を出す観測側（定期的にゲートの状態を読む側。ロックを取らず、書き込まず、GET を妨げない）があります。この通知の「消える条件」で、独立レビューが 7 回続けて新しい穴を見つけました。最新（第 7 回）の指摘はすべて「資源の終了異常（SQLite の close、ロックの close/unlock、所有プールの cleanup）の取りこぼしと、どちらの側（local／shared）の異常かという帰属の誤り」の型で、第 8 回はその全資源を棚卸しして共通部品にまとめた修正です。第 7 回の指摘: (1) 入れ子の二重ゲートで、外側ローカルの終了異常に内側の shared が帰属され、誤った側の観測で通知が早期に消える (2) 取得側の R/W SQLite の close が失敗し続けても観測側は open を返し通知が消える (3) 標準 HTTPS 経路で所有プールの owner.cleanup() が失敗すると、上限 3 の 429 停止が成立せず次の取得が実行される (4) 最終確認で検出した新しい STOP の通知が次の周期まで遅れる。

見てほしい点（コードを読んで、根拠つきで）:
1. 上の指摘が本当に直っているか（再現シナリオごとに、該当コードと試験を読む）。
2. 終了処理の共通部品の取りこぼし: 取得・観測が確保する全資源（SQLite 接続［R/W・immutable］、ロックファイル、番兵、所有マーカー、owned_https のプール、Draft トランスポート、入れ子の local/shared ゲート）で、終了の例外が一次結果（429・結果不明・永続 STOP・許可拒否）を上書き・消去していないか。帰属が失敗した資源の所有元になっているか。
3. 取得側が拒否・失敗するときに観測側が open と言わないか（取得と観測の検査の食い違い）。観測側が GET を妨げない・書き込まない・ロックを取らない原則が守られているか。
4. **安全性: 取得許可・429 即停止・二重送信防止・結果不明の取りこぼしを、この差分が弱めていないか**（許可が増える方向の変更がないか）。
5. 試験が実装の写しでないか、状態爆発・再試行ループ・UI スレッドのブロックがないか。
6. 新しい欠陥。

形式: 総評（3 行以内）、High／Medium／Low の指摘の表（ファイル:行、再現シナリオ、根拠、提案）、統合可否（可／条件付き／不可）。確認できない点は推測と明記。最後に次を出力して終了:
