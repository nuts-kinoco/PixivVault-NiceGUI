背景: アプリには「取得停止ゲート」があります。Pixiv への GET が 401/403/429 になったり、結果が分からない（通信結果不明）状態になったりしたら、通信を止めて固定の通知（未解消のあいだ消えない）を出し、原因が解消したと確認できたときだけ通知を消します。ゲートの取得側（実際に GET を許可するか判断する側）と、通知を出す観測側（定期的にゲートの状態を読む側。ロックを取らず、書き込まず、GET を妨げない）があります。この通知の「消える条件」で、独立レビューが 7 回続けて新しい穴を見つけました。最新（第 7 回）の指摘はすべて「資源の終了異常（SQLite の close、ロックの close/unlock、所有プールの cleanup）の取りこぼしと、どちらの側（local／shared）の異常かという帰属の誤り」の型で、第 10 回はその全資源を棚卸しして共通部品にまとめた修正です。第 7 回の指摘: (1) 入れ子の二重ゲートで、外側ローカルの終了異常に内側の shared が帰属され、誤った側の観測で通知が早期に消える (2) 取得側の R/W SQLite の close が失敗し続けても観測側は open を返し通知が消える (3) 標準 HTTPS 経路で所有プールの owner.cleanup() が失敗すると、上限 3 の 429 停止が成立せず次の取得が実行される (4) 最終確認で検出した新しい STOP の通知が次の周期まで遅れる。

**前回（第 8 回）のあなたの判定は「統合不可」でした（H01 停止確定前に間隔待ちへ入った別取得が送信へ進める、M01 最終再読で得た STOP が照合失敗で消える、M02 アイドルタイマーの終了異常が製品入口で固定通知に届かない、M03 R/W SQL だけの継続異常を観測が open と扱う、M04 旧リーダーの選択証明の合算で通知が解除不能、L01）。第 9・10 回はこれらへの修正です**（第 9 回: 待機明け・再試行・取得ゲート通過後・HTTPS 接続確立後の停止再確認、公開 GET 入口でのアイドル終了異常の固定通知、最終確認の SQLite 再評価。第 10 回: M01・M03［無ロックの immutable 接続で取得側と同じ SQL 検査］・M04［旧リーダーの選択証明を現世代の解除条件から外す・ゲート交換時の確認回数リセット］・L01）。自己申告の数値（修正前 13 件失敗→修正後 13 件合格、重点 552 件合格、全体 5,342 件合格・3 件失敗＝おすすめ画面の 90 秒タイムアウト／設定ダイアログの NiceGUI 起動失敗／20,000 件描画の閾値超過、いずれも単独再試験で通過）は OUTCOME.md にあります。ログ原本は軽量ブランチに含めていないので、404 は想定どおりです。

見てほしい点（コードを読んで、根拠つきで。まず第 8 回の H01・M01〜M04・L01 が直っているかを 1 件ずつ判定）:
1. 上の指摘が本当に直っているか（再現シナリオごとに、該当コードと試験を読む）。
2. 終了処理の共通部品の取りこぼし: 取得・観測が確保する全資源（SQLite 接続［R/W・immutable］、ロックファイル、番兵、所有マーカー、owned_https のプール、Draft トランスポート、入れ子の local/shared ゲート）で、終了の例外が一次結果（429・結果不明・永続 STOP・許可拒否）を上書き・消去していないか。帰属が失敗した資源の所有元になっているか。
3. 取得側が拒否・失敗するときに観測側が open と言わないか（取得と観測の検査の食い違い）。観測側が GET を妨げない・書き込まない・ロックを取らない原則が守られているか。
4. **安全性: 取得許可・429 即停止・二重送信防止・結果不明の取りこぼしを、この差分が弱めていないか**（許可が増える方向の変更がないか）。
5. 試験が実装の写しでないか、状態爆発・再試行ループ・UI スレッドのブロックがないか。
6. 新しい欠陥。
