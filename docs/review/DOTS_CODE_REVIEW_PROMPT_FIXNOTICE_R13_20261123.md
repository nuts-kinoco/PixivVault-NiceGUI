背景: アプリには「取得停止ゲート」があります。Pixiv への GET が 401/403/429 になったり、結果が分からない（通信結果不明）状態になったりしたら、通信を止めて固定の通知（未解消のあいだ消えない）を出し、原因が解消したと確認できたときだけ通知を消します。ゲートの取得側（実際に GET を許可するか判断する側）と、通知を出す観測側（定期的にゲートの状態を読む側。ロックを取らず、書き込まず、GET を妨げない）があります。この通知の「消える条件」で、独立レビューが 7 回続けて新しい穴を見つけました。最新（第 7 回）の指摘はすべて「資源の終了異常（SQLite の close、ロックの close/unlock、所有プールの cleanup）の取りこぼしと、どちらの側（local／shared）の異常かという帰属の誤り」の型で、第 13 回はその全資源を棚卸しして共通部品にまとめた修正です。第 7 回の指摘: (1) 入れ子の二重ゲートで、外側ローカルの終了異常に内側の shared が帰属され、誤った側の観測で通知が早期に消える (2) 取得側の R/W SQLite の close が失敗し続けても観測側は open を返し通知が消える (3) 標準 HTTPS 経路で所有プールの owner.cleanup() が失敗すると、上限 3 の 429 停止が成立せず次の取得が実行される (4) 最終確認で検出した新しい STOP の通知が次の周期まで遅れる。

**前回（第 12 回、あなたの判定: 統合不可）の指摘**: High R12-H01（保存済みプロファイルの再発拒否が、通知解除を止める世代に反映されず、先行した明示再確認で通知が消える）、Medium R12-M01（正常な長い GET 中の busy 観測で、取得成功の解除証拠を捨てる）、Low R12-L01（再確認できない異常だけでもボタンが出る）。別の AI の検証では、番兵作成不能（ENOSPC）でも再確認で通知が消える、再確認中の並行拒否が記録前だと取りこぼし、ゲート交換後に旧通知が解除不能、同一経路の閉鎖済みリーダーで確認が永久失敗、が見つかった。

**第 13 回は、本人が承認した「縮小版」への切替**です（12 回の往復で収束しなかったため、複雑な自動解除の仕組みそのものをやめた）: ① 観測側は**検出と表示だけ**（自動解除しない。世代・選択証明・解除回数による自動解除は削除・無効化）。② 固定通知は**利用者の明示確認「取得停止を再確認」でのみ解除**。③ 明示確認は**取得側の許可確認と同一の経路**（共有番兵の作成・書込み・同期・除去まで実行、**送信はしない**）をそのまま通し、成功したときだけ解除。④ 取得側の拒否の発生を示す**単調な世代**（通知記録の前に進める）を再確認の開始時と解除時で比較し、並行拒否の競合を封じる。⑤ 正式なゲート交換後は、新ゲートでの再確認の成功で旧通知を解除できる。⑥ 再確認できない異常のみのときは「停止は維持中」と示す。完了条件（本人承認済み）: (1) 取得側が拒否している間は通知が消えない (2) 消えるのは取得側の成功か利用者の明示確認のとき (3) 新規の異常は 1 周期以内に表示。429 即停止・安全性は変えない。M02（送信開始後・応答前の失敗）は基点の既存制約として変更しない決定。自己申告（OUTCOME.md と、red.txt／focused.txt／full.txt ほかのログを軽量ブランチに同梱）: 第 12 回候補に対する新規回帰が 14 件失敗→修正後の関連試験 84 件通過、P6 未照合 0・実通信 0、全体 5,416 件通過・2 失敗（おすすめ画面のタイムアウトと設定ダイアログの NiceGUI 起動。標準 Edge では単独再試験もタイムアウト、既存の Playwright Chromium を明示した単独再試験では両方通過）。src／tests／tools の git tree ハッシュは実行候補 1cdedbfe と提出ブランチで一致（監督が確認）。

2. 終了処理の共通部品の取りこぼし: 取得・観測が確保する全資源（SQLite 接続［R/W・immutable］、ロックファイル、番兵、所有マーカー、owned_https のプール、Draft トランスポート、入れ子の local/shared ゲート）で、終了の例外が一次結果（429・結果不明・永続 STOP・許可拒否）を上書き・消去していないか。帰属が失敗した資源の所有元になっているか。
