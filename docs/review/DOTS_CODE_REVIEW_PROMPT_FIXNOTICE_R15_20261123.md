背景: アプリには「取得停止ゲート」があります。Pixiv への GET が 401/403/429 になったり、結果が分からない（通信結果不明）状態になったりしたら、通信を止めて固定の通知（未解消のあいだ消えない）を出し、原因が解消したと確認できたときだけ通知を消します。ゲートの取得側（実際に GET を許可するか判断する側）と、通知を出す観測側（定期的にゲートの状態を読む側。ロックを取らず、書き込まず、GET を妨げない）があります。この通知の「消える条件」で、独立レビューが 7 回続けて新しい穴を見つけました。最新（第 7 回）の指摘はすべて「資源の終了異常（SQLite の close、ロックの close/unlock、所有プールの cleanup）の取りこぼしと、どちらの側（local／shared）の異常かという帰属の誤り」の型で、第 15 回はその全資源を棚卸しして共通部品にまとめた修正です。第 7 回の指摘: (1) 入れ子の二重ゲートで、外側ローカルの終了異常に内側の shared が帰属され、誤った側の観測で通知が早期に消える (2) 取得側の R/W SQLite の close が失敗し続けても観測側は open を返し通知が消える (3) 標準 HTTPS 経路で所有プールの owner.cleanup() が失敗すると、上限 3 の 429 停止が成立せず次の取得が実行される (4) 最終確認で検出した新しい STOP の通知が次の周期まで遅れる。

**前回（第 14 回、あなたの判定: 統合不可、High 0・Medium 2）の指摘**: R14-M01（観測が再確認自身の番兵を通信結果不明として固定し得る＝誤検出）、R14-M02（競合除外時に別対象の観測不整合まで落とす＝取りこぼし）。別の AI の検証でも、バイトロックの OS エラーから型付き例外への変換前に窓があり拒否世代が進む前に通知が消える、gate._exclusive の外の共有オーナー確認・選択 Cookie 確認・旧履歴確認の拒否が世代を進めない、複数の確認候補で先行の拒否が後続の成功で打ち消される、初回未設定時の同一理由の通知の重複、が見つかった。

**第 15 回の構造**（縮小版の続き。縮小版＝観測側は検出と表示だけで自動解除しない／固定通知は利用者の明示確認「取得停止を再確認」でのみ解除／明示確認は取得側の許可確認と同一の経路で、送信はしない。完了条件［本人承認済み］: (1) 取得側が拒否している間は通知が消えない (2) 消えるのは取得側の成功か利用者の明示確認のとき (3) 新規の異常は 1 周期以内に表示。429 即停止・安全性は変えない。M02［送信開始後・応答前の失敗］は基点の既存制約で変更しない決定）: ① **拒否は OS エラーの捕捉点で物理ゲートごとに記録**（型付き例外への変換前。gate._exclusive の外の共有オーナー確認・選択 Cookie 確認・旧履歴確認も共通の入口）。再確認中に同じゲートで拒否が成立したら解除しない。② **再確認の所有を番兵作成前に登録**し、再確認と重なった観測は**対象ゲート分だけ破棄**、別ゲートの異常は同じ周期に表示。③ 解除には**稼働中の全候補の成功**を要求。④ 初回起動時の同一理由・同一対象の通知は 1 件にまとめる。**自己申告が残す未解決**: 全体 pytest の 1 回目で 53 件失敗（初回起動の旧履歴処理に今回入った回帰。修正後は失敗した 51 件を含む再試験 78 件すべて合格、残るブラウザ 2 件は環境起因で単独通過）。最終候補の全体 pytest は監督が実行中で、結果は後で照合します。Argon の Low「単一ゲートリーダー［ローカル専用と共有専用］が別々に同一ポリシーへ登録されたとき、観測由来の durable_gate が合体すると再確認不能になる」は今回の対応に含めず統合判断に残してある。自己申告の数値: 修正前 13 件失敗・3 件合格（追加の境界試験 3 件も失敗）、関連 110 件合格、最終境界・P6 28 件合格、P6 未照合 0・実通信 0。OUTCOME.md と主なログは軽量ブランチの verify/fix-notice-20261122/r15 に同梱。src／tests／tools の git tree ハッシュは実行候補 4660a2ec と提出ブランチで一致（監督が確認）。

見てほしい点（コードを読んで、根拠つきで。まず第 12 回の High・Medium・Low が縮小版で解消または不要になったかを 1 件ずつ判定）。特に (a) **自動解除が本当に無くなっているか**（取りこぼしの経路・残骸）、(b) **明示再確認が許可を増やさず、番兵・ゲート状態を壊さないか**（書込みを伴うので、取得と同じロック下か）、(c) 複数リーダー・閉鎖済みリーダーで解除不能にならないか:
1. 上の指摘が本当に直っているか（再現シナリオごとに、該当コードと試験を読む）。
2. 終了処理の共通部品の取りこぼし: 取得・観測が確保する全資源（SQLite 接続［R/W・immutable］、ロックファイル、番兵、所有マーカー、owned_https のプール、Draft トランスポート、入れ子の local/shared ゲート）で、終了の例外が一次結果（429・結果不明・永続 STOP・許可拒否）を上書き・消去していないか。帰属が失敗した資源の所有元になっているか。
3. 取得側が拒否・失敗するときに観測側が open と言わないか（取得と観測の検査の食い違い）。観測側が GET を妨げない・書き込まない・ロックを取らない原則が守られているか。
4. **安全性: 取得許可・429 即停止・二重送信防止・結果不明の取りこぼしを、この差分が弱めていないか**（許可が増える方向の変更がないか）。
5. 試験が実装の写しでないか、状態爆発・再試行ループ・UI スレッドのブロックがないか。
6. 新しい欠陥。
