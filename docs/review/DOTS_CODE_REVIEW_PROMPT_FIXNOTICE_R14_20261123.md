背景: アプリには「取得停止ゲート」があります。Pixiv への GET が 401/403/429 になったり、結果が分からない（通信結果不明）状態になったりしたら、通信を止めて固定の通知（未解消のあいだ消えない）を出し、原因が解消したと確認できたときだけ通知を消します。ゲートの取得側（実際に GET を許可するか判断する側）と、通知を出す観測側（定期的にゲートの状態を読む側。ロックを取らず、書き込まず、GET を妨げない）があります。この通知の「消える条件」で、独立レビューが 7 回続けて新しい穴を見つけました。最新（第 7 回）の指摘はすべて「資源の終了異常（SQLite の close、ロックの close/unlock、所有プールの cleanup）の取りこぼしと、どちらの側（local／shared）の異常かという帰属の誤り」の型で、第 14 回はその全資源を棚卸しして共通部品にまとめた修正です。第 7 回の指摘: (1) 入れ子の二重ゲートで、外側ローカルの終了異常に内側の shared が帰属され、誤った側の観測で通知が早期に消える (2) 取得側の R/W SQLite の close が失敗し続けても観測側は open を返し通知が消える (3) 標準 HTTPS 経路で所有プールの owner.cleanup() が失敗すると、上限 3 の 429 停止が成立せず次の取得が実行される (4) 最終確認で検出した新しい STOP の通知が次の周期まで遅れる。

**前回（第 13 回、あなたの判定: 統合不可）の指摘**: High R13-H01（共有ゲートの拒否世代が認証と通常取得で別で、解除時の判定をすり抜ける）、Medium R13-M01（再確認が作った番兵を、競合する読取が通信結果不明と誤認し、固定通知を増やす）。別の AI の検証では、同一ポリシーでも解除直前のロック拒否を取りこぼす（拒否側が世代を進めるため状態ロックを待つ間に再確認が旧通知を削除）、初回 Native 認証がリーダー登録前に拒否されると監視が始まらない、再確認自身の「再確認不能」な終了異常が同じクリックで失われる、も見つかった。

**第 14 回の構造**（縮小版の続き。縮小版＝観測側は検出と表示だけで自動解除しない／固定通知は利用者の明示確認「取得停止を再確認」でのみ解除／明示確認は取得側の許可確認と同一の経路で、送信はしない。完了条件［本人承認済み］: (1) 取得側が拒否している間は通知が消えない (2) 消えるのは取得側の成功か利用者の明示確認のとき (3) 新規の異常は 1 周期以内に表示。429 即停止・安全性は変えない。M02 は基点の既存制約で変更しない決定）: ① **物理 DB・ロックの ID をキーにしたプロセス全体の拒否世代を、拒否の発生点で原子的に進める**（状態ロックを経由しない）。再確認は開始時と解除直前にこの世代を比較。② 監視は、リーダー登録の有無に依存せず、固定通知が 1 件でもあれば開始（Native 初回認証の登録前拒否を含む）。③ 再確認は全候補（複数リーダー・閉鎖済みを含む）の結果を集約し、再確認不能な終了異常が 1 つでもあれば解除せず理由を残す。**自己申告が残す未解決**: OS のロック取得から所有情報の登録までの短い区間で、観測が正常な再確認を競合として表示する可能性／全体 pytest の 3 失敗（おすすめ画面の子プロセスタイムアウトが Chromium 指定でも 1 回、世代切替中の PermissionError が単独再試験で再現せず）。自己申告の数値: 修正前 7 ケース失敗、関連一式 969 件通過、固定候補の入口・P6 試験 45 件通過、P6 未照合 0・実通信 0、全体 5,430 件通過・3 失敗。OUTCOME.md と主なログは軽量ブランチの verify/fix-notice-20261122/r14 に同梱。src／tests／tools の git tree ハッシュは実行候補 40c626ed と提出ブランチで一致（監督が確認）。

見てほしい点（コードを読んで、根拠つきで。まず第 12 回の High・Medium・Low が縮小版で解消または不要になったかを 1 件ずつ判定）。特に (a) **自動解除が本当に無くなっているか**（取りこぼしの経路・残骸）、(b) **明示再確認が許可を増やさず、番兵・ゲート状態を壊さないか**（書込みを伴うので、取得と同じロック下か）、(c) 複数リーダー・閉鎖済みリーダーで解除不能にならないか:
1. 上の指摘が本当に直っているか（再現シナリオごとに、該当コードと試験を読む）。
2. 終了処理の共通部品の取りこぼし: 取得・観測が確保する全資源（SQLite 接続［R/W・immutable］、ロックファイル、番兵、所有マーカー、owned_https のプール、Draft トランスポート、入れ子の local/shared ゲート）で、終了の例外が一次結果（429・結果不明・永続 STOP・許可拒否）を上書き・消去していないか。帰属が失敗した資源の所有元になっているか。
3. 取得側が拒否・失敗するときに観測側が open と言わないか（取得と観測の検査の食い違い）。観測側が GET を妨げない・書き込まない・ロックを取らない原則が守られているか。
4. **安全性: 取得許可・429 即停止・二重送信防止・結果不明の取りこぼしを、この差分が弱めていないか**（許可が増える方向の変更がないか）。
5. 試験が実装の写しでないか、状態爆発・再試行ループ・UI スレッドのブロックがないか。
6. 新しい欠陥。
