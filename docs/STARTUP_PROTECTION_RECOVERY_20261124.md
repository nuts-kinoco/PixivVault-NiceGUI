# 起動保護からの正式復旧手順（2026-11-24）

この手順は監督と本人の承認後に使う。2026-11-24 の実測では、局所と Windows ユーザー共有の両 STOP がともに HTTP 401・revision 1 で、共有ゲートに送信中の記録が残存していた。共有 seal は正式移行形式。設定が NULL だった保全版は revision 38。追加の読取時点では revision 39 で両設定が保存済みだった。 [原因分析](../verify/startrecover-20261124/OUTCOME.md)

## 1. 復旧前の確認と保全

1. 監督は、運用中の候補と対象 Native プロファイル、共有ゲートを使う全取得処理、現在の書き手、適用予定のコミットを確認する。操作の担当を決め、稼働中の取得処理と復旧操作が重ならないことを確認する。外向き通信の予算は本人承認まで 0 件とする。
2. プロファイル、保存元、共有 owner の seal・DB・lock・移行履歴・送信中の記録を一組で保全する。SQLite は書き手の終了と sidecar の有無を確認し、コピー上で整合性と行を確認する。元ファイルの OS 上の同一性、状態と revision、内容の照合を記録する。
3. 現 seal の形式を確認する。正式移行形式で起動用アンカーと起動レコードの両方が欠けている場合は、製品の来歴検査が従来形式として通過する。今回の現物でも通過し、11月17日の退避にある起動用記録は現 seal の証明値に一致しなかった。両方必要な初回起動形式の owner で欠落を観測した場合は、実施を止め、監督が既存 owner と全履歴を独立レビューに回す。 [来歴検査](../src/pixivvault_nicegui/managed_network_stop_startup.py#L42)

## 2. 設定の保存

1. 安全化差分の独立レビュー後、監督は修正版が実際に使われる候補を確認する。既に revision 39 の両参照が本人指定どおりなら、再保存を省ける。保存が必要なら、「PixivVault — 起動設定の確認」の認証無効な保護分岐で、本人確認済みの Cookie ファイルと保存先親を選ぶ。選択だけでは画面内の下書きである。
2. 「保存」を押し、成功表示と保存後の再読込で設定と revision を確認する。書き込みは所有済みプロファイルの設定 SQLite のトランザクションに限られる。設定行・関連設定・既存の Cookie 選択来歴を、保存値を検証したうえで revision CAS で更新する。変更がなければ revision は増えない。修正候補の認証無効分岐は保存後の認証チェックを予約しない。認証を許可する画面の保存では、従来の確認が予約される。 [保存処理](../src/pixivvault_nicegui/ui/native_profile_view.py#L342)・[認証許可と保存後の処理](../src/pixivvault_nicegui/native_startup.py#L257)・[CAS](../src/pixivvault_nicegui/native_profile.py#L447)
3. 保存競合が出た場合は閉じて再読込し、現在の revision と選択値を確認してから本人判断を受ける。保存結果が不明なら、結果を読んでから次の操作を決める。設定値のロールバックが必要な場合は、本人が確認した参照値を、現在の revision を前提とした同じ保存経路で戻す。朝の SQLite を上書きすると revision と選択来歴を巻き戻すため、朝のコピーは照合に使う。

## 3. STOP を保持した再起動と分岐

1. 監督は、保全とレビューがそろい、本人が承認した後に正規手順で終了・再起動を一度行う。通常起動はローカル設定、保存先の所有状態、選択済み保存元と共有 STOP を照合する。起動中に新規保存領域の所有情報を作る場合があり、両 STOP の準備で局所 STOP を共有へ単調に転記する。通常画面に進むと認証確認・ウォームアップ等が取得を試み得る。現401が維持されていればゲートが外向き GET を拒否する。状態変化や所有者不明があれば再起動を重ねず、通信を封じたまま証拠を採取する。 [起動時のローカル・共有検査](../src/pixivvault_nicegui/bootstrap.py#L983)・[局所 STOP の転記](../src/pixivvault_nicegui/managed_network_stop_startup.py#L167)・[認証開始](../src/pixivvault_nicegui/native_startup.py#L580)
2. 通常画面の場合は、10タブの表示、保存値の永続、両 STOP の状態と所有ファイルの同一性、外向き GET 0 を別々に確認する。保護画面が続く場合は、表示された理由、稼働候補、設定 revision、検査に失敗した箇所を記録する。今回の隔離再現では、正式移行形式・両401と標準の送信中記録だけなら通常ルートを登録できた。実機の失敗理由は確認を要する。
3. 「停止履歴の確認と移行手順を開く」から「選択済み保存元の停止履歴を確認する」を選ぶと、現在の Native と設定済み媒体の、読み取れる STOP を表示する。ファイルは読み取り専用で、GET や STOP／seal の書き込みは発生しない。旧媒体までの網羅や取得許可は別途確認する。 [StopRecoveryPanel](../src/pixivvault_nicegui/ui/stop_recovery_view.py#L79)・[履歴を読む範囲](../src/pixivvault_nicegui/native_startup.py#L232)
4. 「正式移行を実行する」は移行ダイアログを開く入口。「内容を確認」は読み取りで、設定済み・追加・過去ジャーナルの保存元を列挙して識別情報と STOP 状態を照合する。「確認した内容で正式移行を実行」は本人の全件確認を必要とし、既存の移行先があれば target_exists で拒否する。判定に先立ち移行先の親に起動・移行ロックを作成する場合がある。新規移行先に対しては停止記録と設定コピーを検証し、停止状態を持つ共有DB、seal、移行記録、アーカイブ、ジャーナルを作成する。Native 側の STOP が未作成で許容される場合に限り、局所のDB・lock・マーカーも公開する。処理内の GET は 0。**今回の共有移行先は既存のため、正式移行の実行は復旧に使えない。** [プレビュー・排他](../src/pixivvault_nicegui/managed_stop_migration.py#L247)・[実行と公開](../src/pixivvault_nicegui/managed_stop_migration.py#L392)
5. 「中断した移行を確認」は、同じプロファイルと既存の移行ジャーナルを照合し、公開済みなら検証後に完了を記録する。未公開なら本人確認済みの移行が追加した Native 側のファイルだけを、証明と排他を再確認して元のステージへ戻す。処理内の GET は 0。公開結果が不明、ファイルが変化、または recovery_conflict なら、その状態を保全して監督へ渡し、再実行を重ねない。 [ロールバック](../src/pixivvault_nicegui/managed_stop_migration.py#L347)・[中断の回復](../src/pixivvault_nicegui/managed_stop_migration.py#L569)
6. 「取得停止の確認・回復」は、共有 STOP が未停止のときに残った、結果不明の送信中記録を扱う。正式 owner と取得と同じロックの下でプレビューを再検査し、本人確認後に標準の送信中記録を同じ owner 内の acknowledged-get-*.v1 へ退避する。その操作は GET を発生させず、STOP 行を変更しない。操作者が回復後に改めて取得を行う場合は、その時点のゲート判定が必要。**今回のように401で停止済みなら、プレビュー段階で拒否される。** 「取得停止を再確認」も所有・ゲートの現在状態と通知を確認する処理で、401のラッチを解除しない。 [送信中記録の回復](../src/pixivvault_nicegui/managed_network_stop_shared_scope.py#L295)・[再確認](../src/pixivvault_nicegui/ui/request_status_view.py#L163)

## 4. 401 の判定と失敗時の扱い

- 最終採用世代は 19:14:58 更新、共有の送信中記録は 20:28:36.132、共有 STOP DB は 20:28:36.372、局所 STOP DB は 20:28:36.385 更新。401 は最後の採用より後で、無効化・失効・不正な資格を疑う根拠になる。どの取得経路がどの資格を使って応答を受けたかのログがなければ、その世代が失効したとまでは確定できない。時刻からの推測だけで資格を試さない。
- 現行の正式移行、結果不明の回復、設定保存、再起動はいずれも既存の401を解除する操作を提供しない。新しい Cookie の選択は設定として扱い、既存 STOP は保持する。通信までの復旧には、監督の独立レビューを経た製品の対応方法と本人による明示承認、送信予算、失敗時の停止条件が必要。
- 保全コピーは検証や隔離再現に使える。共有 owner のDB・lock・seal をファイル単位で戻すと、移行の順序、ファイル同一性、より新しい STOP が失われ得る。現物の復元を判断する場合は、本人承認と独立レビューの下で、全書き手・全取得経路の排他、元データとSTOP履歴の単調保持、復元後の同一性を先に立証する。製品内の回復処理で完結しない失敗は、保全した状態のまま止める。

## 実機へ適用する前の追加条件（2026-11-27 監督、独立レビューの指摘 3-1・3-2）

- 実機を再起動する前に、保全コピーで作った複製環境で「設定の保存 → 終了 → 再起動」を先に実行し、状態の遷移を確かめる（複製での先行実証は必須で、省略しない）。
- 実機では「正式移行を実行する」「中断した移行を確認」「取得停止の確認・回復」を押さない。画面の案内がこれらを勧めても押さず、監督に戻す。
