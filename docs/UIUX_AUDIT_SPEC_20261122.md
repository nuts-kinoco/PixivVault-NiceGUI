# UI/UX 完全監査の仕様（2026-11-22、本人指示）

目的: 「ツッコミが入らない」状態にしてから本人に見せる。基準は (1) 元 Flet のデザイン契約（元が正）、(2) 既存タブとのトンマナの一致、(3) Apple Human Interface Guidelines（日本語版 https://developer.apple.com/jp/design/human-interface-guidelines/）の原則。PV は Web UI（NiceGUI）で、主にデスクトップのポインター操作なので、HIG の macOS 向けの値を既定にし、タッチ向けの値は参考にする。

**出典の範囲（正直に）**: アクセシビリティ・ボタン・タイポグラフィの 3 ページは本文を取得して数値を確認した（developer.apple.com/tutorials/data/design/human-interface-guidelines/*.json）。メインページと他のページの本文は取得できず、色・レイアウト・アラート・空状態・読み込み・入力・キーボードの項目は一般的な HIG の知識による（数値を出さない）。

## B. 目で見て判定する項目（Neon・Argon・監督が画像で）
- **B1 階層**: 最初の 1 画面で「何をする画面か」「主操作は何か」が 2 秒で分かる。主操作が最初の画面に収まる。
- **B2 一貫性（調和）**: 同じ役割の部品（更新・再試行・サイズ切替・期間チップ・スイッチ・空状態・状態表示・ダイアログ）が全画面で同じ見た目・同じ位置。追加タブと既存タブで見出し・ツールバー・余白の様式が揃う。
- **B3 元 Flet とのズレ**: 元の画面（並置画像）と比べて、デザイン変更・機能の退行がない。元に無い画面は、既存タブの様式に倣う。
- **B4 無駄な縦長・ボタンの羅列**: 縦に伸びた空白、意味なく積まれた説明文、順序づけのない操作の並び、状態ラベルの分散がない。
- **B5 空状態・エラー・読み込み**: 何も無い理由と次の行動を示す。エラーは何が起きたか・どう直すかを平易に（謝罪や曖昧語なし）。処理が長いときは進捗・待つ理由を示す（真実の状態表示）。
- **B6 文言**: 平易な日本語。専門語や内部名（API の名前、ファイル名、内部エラーコード）を画面に出さない。確認ダイアログは「何が起きるか」「取り消せるか」を書く。
- **B7 ライト・ダーク**: 同じ情報構造。暗い・明るい背景でアイコン・画像・境界線が見える。
- **B8 余白とリズム**: 余白が 4／8／12／16／24px 系の段階に乗る。揃っていない直書きの値を使わない。

## C. 合格条件（本人に見せる前の関門）
1. A の全項目で違反 0（例外は理由つきの台帳に載せ、本人に見せても説明できるもの）。
2. B で Neon・Argon の独立監査が、**全画面で High 0・Medium 0**（Low は台帳に）。
3. 並置画像と計測を監督が全枚確認し、気になる点を 0 にする。
4. 実機アプリ（NiceGUI ネイティブ窓）で、代表画面（設定・定期チェック・メタデータ・カスタムランキング・おすすめ・学習・重複整理・ライブラリ・ダウンロード・キュー・失敗リスト・閲覧履歴・各ダイアログ）を、ライト・ダークで目視。
5. 以上を満たしてから、本人に「見てほしい」と連絡する。

## 追加（2026-11-22 本人の指摘）: コンテンツ（画像）の表示面積
本人が実機で使い、「カスタムランキング」で、タブ・見出し・ツールバー・「よく効くタグ」・状態行・検索欄が画面の約半分を占め、画像の表示範囲が狭くて見づらいと指摘した（1920×1030 前後の窓で、画像の先頭行がほぼ 500px の位置から始まる）。UI/UX に関わる重要な項目。HIG の「控えめ（deference）」の考え方: UI はコンテンツを理解し操作する助けになるべきで、コンテンツと競わない。
- **A17 コンテンツの表示面積**: 画像・カードの一覧を主役とするタブ（ランキング、カスタムランキング、ライブラリ、マイブックマーク、おすすめ、重複整理、閲覧履歴、ダウンロードの作者一覧など）で、最初の画面に占める「画像・カード領域」（スクロール領域の可視部分）の割合を測る。しきい値（暫定）: 1280×800 で 55% 以上、1920×1080 で 60% 以上。**学習タブは現在の大きさ（画像の表示領域）を下限として、これを下回らない**（基準値は修正前の実測。現状の学習タブは画像が大きく見えていて、本人が最低限担保したいとした）。
- **B9 クロームの控えめさ**: ヘッダー・タブ・ツールバー・状態行・検索欄（クローム）は、使うときだけ展開し、普段は 1〜2 行に収める。同じ役割の折りたたみは全タブで同じ部品・同じ挙動（トンマナ）。展開・折りたたみの状態は覚える。スクロールで自動的に隠れる（下へ=隠す、上へ=出す）案も評価する。
- 元 Flet のデザイン契約との関係: 本人の直接の要望なので、画像の表示面積のために、ヘッダー・ツールバーの密度や構成を変えてよい。ただし、機能・操作・文言（意味）は残し、元の色・書体・部品の様式は保つ。変更は 1 つの共通部品（折りたたみ可能なツールバー）にまとめ、全タブで揃える。

## 追加（2026-11-22 Dots・muse の独立レビューを受けて）
- **標準倍率の定義**: 標準 = OS のスケーリング 100% 相当（ビューポート 1280 CSS px 以上でタブ 1 行）。Windows の 125% スケーリングは実効 1024 CSS px で、タブは等幅 5×2 の 2 段にしてよい。**A16/A17 の計測に、1024×768 と「1280×800 の 125%（実効 1024×640）」を加える**。
- **A17 の補助指標**: 割合だけでなく、「初画面に見える作品（カード）数」と「画像そのものの可視寸法（px）」を記録する（空白や縮小カードで割合だけ達成するのを防ぐ）。1024×768 の暫定しきい値は 40% 以上。
- **A17 の 125% 判定**: 実効 1024×640 では、通常と長文 DB 警告＋取得停止＋未解消の失敗 2 件の併発に対して、絞り込みを畳んだ状態の合格を必須とする。展開状態は参考値として計測する。しきい値は、同倍率・同条件の改修前の現行 Flet 並置と現行 NiceGUI を製品で測って決める。
- **200% の判定**: 実効 640 CSS px 幅では A11（操作の到達性）と暫定目標で判定する。A17 の面積割合は参考値とする。長文 DB 警告・取得停止・失敗 2 件の併発時も、一覧で完全に見える画像を 1 枚以上確保する。学習画像は可視幅×高さを測って製品の下限と比較し、判定四択の到達性と操作は別に判定する。10 画面のナビは開閉式でもよい。DB 警告・取得停止の入口・未解消件数は閉じた状態でも表示する。
- **学習タブ**: 画像の可視寸法（1280×800 で 618.6×464.0 px、1920×1080 で 1042.6×782.0 px）を下回らないことと、**判定の四択（見送る・合わない・いいね・SuperLike）が常に到達できること**を、独立した合格条件にする。
- **統合ヘッダーの検証**: 最終のタブ名・右上のアイコン（自動処理を含む）・本番 DB の警告・取得停止の確認と復旧の入口を、**1 つの画面で同時に**、1280／1920 と 200% 拡大、警告の長文で確認する。取得停止や DB 警告を「その他」に隠さない。
- **自動処理の失敗の見落とし防止**（A13・B5）: 閉じた状態でも「自動処理：未解消 N」を主表示し、「未確認 a／確認済み b」を添える。読み上げ名で総数と内訳を区別し、フォーカスを奪わず role=status で通知する。待機・停止（意図した OFF）・未確認は別の意味で扱い、意図に反する停止と失敗だけを警告系にする。
- **画面の動き**（A14）: 演出を追加する場合もユーザーの動きの抑制設定を優先する。スクロール方向に応じたヘッダー・ツールバーの自動開閉は採用せず、手動折りたたみと固定の安全導線を確認する。
