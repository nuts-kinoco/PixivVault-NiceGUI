# 段階移植の計画

元計画: ユーザー承認の `PixivVault_NiceGUI_Migration_Plan_2026-10-22.md`。
作業開始承認: 2026-10-22。公開push、複数チャットの分担、小単位の検証・コミット、新アプリのCoS経由のデスクトップ/ブラウザ操作を許可。

## フェーズと受入

| 段階 | 成果物 | 完了の判定 |
|---|---|---|
| 0 基準固定 | 現行の操作台帳、画像・固定データ・計測条件 | 同じ条件で新旧を比較でき、未検証項目を識別できる |
| 1 シェルとWindows | 現行デザインの部品、独立入口、最小native配布 | 実機の起動/終了/DPI/フォーカス/最小化・復帰が通る |
| 2 必要な境界分離 | 画面状態、画像取得、通知、ジョブ状態 | UIからDBやワーカーの寿命を分離し、旧挙動を維持する |
| 3 代表経路 | ランキング→絞込→追加表示→ビューア→戻る | 同じ実画像・表示密度で外観・操作・p95性能に合格 |
| 3b 学習の早期試験 | テストデータで4判定・連打・Undo | 二重記録・古い画像への判定・取消順序の破れがない |
| 4 閲覧系展開 | ライブラリ/作者/ブクマ/類似/おすすめ | 主要操作と再訪状態復元が通る |
| 5 更新系展開 | 学習全体/DL/キュー/失敗/重複/設定/外部連携 | 結果・保存・停止再開・復旧の互換が通る |
| 6 製品切替 | Windows配布/トレイ/URI/オフライン/長時間試験 | 必須操作・性能・データ互換・切戻しを確認 |

段階0/1の実機確認待ち中も、独立した状態モデル・fixture・単体試験は先に準備できる。
ただしそれを理由に段階0/1が完了したとは記録しない。

## 維持するもの

暗色の階層、青いアクセント、文字・余白・カードの大中小、横タブ、フィルタ、画像の縦横比を維持する。
『もっと見る』を勝手に自動スクロールへ変えない。戻ったときは選択・並び・件数・スクロール位置を復元する。
学習値、Undo、DBスキーマ、ZIP/保存形式、既存APIの制限は移植と同時に変更しない。

## 初回の範囲

1. 独立repo、専用venv、pytestを明示実行するCI、操作台帳。
2. 架空データ、フィルタ/ページング/作品移動、要求世代と遅着破棄の純粋な状態モデル。
3. 同じ配色と余白を起点にしたデモシェル。初期50件だけを構築し、一覧だけを更新する。
4. 自動試験・実ブラウザ試験・独立レビューを通して小単位でpush/PRへ反映する。

初回には実画像の性能比較、実DBの接続、既存非公開ソースの転送、旧アプリの変更を含めない。
現在のデモは『作品間の移動』に加え『作品内の複数ページ移動』を持つ。ズーム/パン・うごイラ・原寸画像・保存操作はまだ製品互換の受入対象として未完。

## 品質ゲート

変更ごとに、担当範囲のテスト→統合pytest→依存検査→静的差分→独立レビューを行う。
試験の結果が変わる修正だけ再実行し、理由のない全件ループを避ける。
単体テスト、HTTP初期描画、実ブラウザ操作、Windows native、性能比較の証拠を分ける。
画面の動作待ちを短く見せるため、未完の処理を成功として表示しない。

## 暫定的な性能目標

目標値であって達成値ではない。現行の実測後に固定する。
入力反応p95 100ms以内、温キャッシュのタブ再訪200ms以内、先読み済み画像の頁送り150ms以内。
重い代表操作は現行p95から20%以上の改善を目標にし、すでに速い操作は悪化させない。
同じPC・画像・件数・DPI・キャッシュ条件で比較し、PythonとWebViewを含む総資源を測る。

## 分担・進捗

同時workerは最大8（ユーザー変更承認）、通常medium。独立した作業だけを並行し、1ファイルの編集者は1人。
難所だけhighを検討し、pro/xhighを常用しない。成功件数を利用枠の消費量へ換算しない。
進捗は受入済み操作/全操作、視覚比較数、性能比較数、重大回帰数で記録する。行数から完成率を出さない。
Git操作・環境変更・統合はprime、workerは担当ファイルと試験・読取レビューのみ。

## 切戻し

新入口は元のPixivVaultを変更しない。同じ本番DBへ二つのUIを同時に書込み接続しない。
本番接続を許可する段階で単一起動とDBの明示パスを設計し、稼働中WALの整合したバックアップを使う。
切戻しのために利用データを古いDBへ自動的に戻さない。
