## 守るべき制約（設計の前提）
1. **元の学習の挙動を壊さない。** GPU 学習は「追加の補助スコア」で、**設定で止められ、無効にすると元の順位付けに完全に戻る**こと（FL-I15 の LocalTagView と同じ原則: 読み取り時の揮発ビュー、永続ストア・検索語を汚さない）。
2. **通信は増やさない。** 自動通信は取得停止ゲート（「取得・更新」と同じ）を通す。Pixiv のレート制限（約 1.15 req/s）を圧迫する先読み増加は不可。GPU 推論の対象は、すでに取得済みの画像（保存済み作品、既存の先読み `LearningImagePrefetch` が取ったもの）に限る。
3. **ローカル完結。** 画像・判定履歴・埋め込みを外部サービスに送らない。依存追加（onnxruntime-gpu、torch、open_clip など）は、導入の重さ・Windows での入手性・RTX 5080（Blackwell、CUDA 12.8 以降）での動作可否・オフライン起動を理由付きで評価する。
4. **Undo・再判定・全削除に追従できる。** スワイプの取り消しや履歴の削除で、学習結果が正しく無効化／再計算されること。
5. **実データを壊さない。** 保存領域・DB への書き込みを増やす場合は、別ファイル・別テーブルで、無くしても本体が動くこと。
6. 起動の重さ・VRAM を他機能（Egara 類似検索、WD タグ付け、アプリ本体）と奪い合わないこと。常駐ではなく、アイドル時・手動・設定でのスケジュールを前提にする。

## 私（Claude）の仮説・アイデア（批判してほしい）
- 判定数が少ない間（数十〜数百）は、深い学習より**埋め込み空間での近傍／プロトタイプ法（正例重心との類似度、負例からの距離）**の方が安定する。MLP は判定が増えてから段階的に有効化するのが安全では？
- skip は「嫌い」ではなく「今は興味がない／すでに見た」を含むノイズ。**hate と skip を別扱い**し、skip は弱い負例か、順位だけに使うのがよいのでは。hate の理由（genre / style）は、どの埋め込み空間（意味 vs 絵柄）に効かせるかのルーティングに使える。
- 保存・ブクマ済みの作品は、正例として大量にある一方、**選択バイアス**（ブクマした理由は絵柄以外もある）を持つ。重みを下げるか、別ヘッドで扱うべきでは。
- **能動学習**: スワイプの提示順に「不確実性が高い候補」や「クラスタ境界の候補」を混ぜると、判定数あたりの学習効率が上がるのでは。ただし体験（探索枠 3 割の設計）を崩さない。
- 評価は、判定履歴の**時系列分割**（過去で学習し直近の判定を予測）で、AUC・NDCG@k・like 率の改善を測る。オンラインの A/B ができない個人利用では、これが唯一の客観指標になるのでは。
- **説明可能性**: 「なぜこれが出たか」（最も近い好み作品 3 枚、近いクラスタ名）を表示できると、GPU 学習の価値が本人に伝わる。
- 嗜好のドリフト（好みが時間で変わる）を、時間減衰と再学習で扱う。
- 微調整（LoRA）は、判定数が数千件でも過学習・忘却・設定 OFF への追従の難しさがあるため後回し、で合っているか。
- 「GPU を使い切る」こと自体は目的化せず、**効果が出る使い方（大量の保存画像の埋め込み事前計算、複数モデルのアンサンブル、定期的な再学習）**に VRAM を使う、という整理でよいか。
