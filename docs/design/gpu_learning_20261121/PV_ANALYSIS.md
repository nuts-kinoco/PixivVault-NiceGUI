## 結論：推奨構成と最初の一歩

**推奨は「EgaraNet ＋ 少数の好みクラスタ ＋ 案A・Dの段階的併用」**。最初から MLP や複数モデルを導入する必要はありません。

1. 最初は保存済み画像と判定履歴で**オフラインのシャドー評価**を行い、現行の順位を変えずに効果を測る。
2. 次に、既存画像から作った作者ベクトル（D）と、通常の先読み画像（A）に限って補助スコアを適用する。追加通信はゼロ。
3. RTX 5080 は EgaraNet の大量推論に優先使用。移植版に既存の CUDA 経路を検証してから、追加モデルの必要性を判断する。
4. **既存の AUC 0.795 は「絵柄の識別性能」であり、「ユーザーの好みの予測性能」ではありません。** ここを混同しないことが最重要です（元リポ `docs/MODEL_SELECTION_2026-08-06.md:509-536`）。

Neon 案の多モデル・クラスタリング・MLP 一括導入には反対です。性能向上の証明より先に、依存関係、GPU負荷、障害時の復帰、評価の難しさを増やしてしまいます。

### 1. A〜Dの比較と、最小構成（MVP）

| 案 | 追加通信 | 効果が届く範囲 | 私の評価 |
|---|---|---|---|
| **A：手元の画像＋既存先読み** | 0 | 保存済み画像、表示のために取得済みの候補 | **本命**。作品単位で絵柄を評価できる |
| B：候補画像を先に大量取得 | 増える | 画像を取得した候補全体 | 初期採用しない。通信・待ち時間・停止制御が重い |
| C：サムネイルで代用 | 既存分なら0 | サムネイルが手元にある作品 | 独立案というより**Aの入力画像の選択肢** |
| **D：作者の絵柄ベクトル** | 0 | その作者の保存画像が手元にある候補 | **補助として有力**。ただし適用範囲と新規性に限界 |

**Dを最初の有力候補とする仮説には、条件付きで賛成です。**

Dなら、作者が分かっているだけの候補に画像取得前から視覚情報を加えられます。しかし、現行の作者Betaスコアも既に「その作者をどれほど好むか」を表現しています。Dで同じ作者を高評価するだけなら、改善というより既存スコアの二重計上です。

そこで、Dの価値は次の条件で判断したいです。

- 同じ作者でも絵柄にばらつきがあり、保存画像から得た視覚的情報が作者Betaとは異なる予測力を持つ。
- 作者の判定件数が少なくても、その作者の保存済み画像が十分にある。
- 作者Betaスコアを固定した比較でも、Dによって新しい好み作品が上位に来る。

一方、**未知作者の発掘にこそ視覚学習を使いたいなら、Dだけでは目的を達成できません。** その作者の画像が1枚も手元になければ、Dの材料がないためです。

MVPは、まず保存済み画像と利用可能な判定画像からEgaraNetの特徴を作り、好意例の近傍・少数プロトタイプによるスコアを**表示に反映せず記録するシャドー評価**とします。そこで作者ベクトルDの追加効果を測り、次に既存先読みAを組み合わせます。

なお移植版では、候補のJSONメタデータは `managed_discovery_candidate` に保存されています。しかし、これは合意書にあった**画像を含む大規模候補プールの実装ではありません**（移植版 `discovery_learning.py:87-114,280-319`）。現状の先読みは順位決定後です（移植版 `ui/learning_view.py:1380-1413`）。

ここを取り違えると「候補を視覚スコアで並べてから先読みする」という、実際には実行できない順番の設計になります。

### 2. EgaraNetのGPU化と、追加モデルの価値

**最初に試すべきなのは、既存のEgaraNet ONNXをCUDAで動かすことです。**

移植版 `egara_inference.py:113-119,158-244` には、既にCUDA/CPUのプロバイダ選択、CUDA失敗時のCPUフォールバック、モデルのSHA-256確認が実装されています。つまり、GPU対応をゼロから設計し直す必要はありません。

RTX 5080はcompute capability **12.0（sm_120）**。現在のONNX RuntimeはCUDA 12.8向けとCUDA 13.0向けで配布物・依存が分かれるため、Python 3.13、Windows、CUDA、cuDNNの組み合わせを固定して検証する必要があります。<Cite refs={["turn666945search3","turn220768search0","turn666945search5"]}/>

「DirectMLのReshape問題があるからGPU化は難しい」という見方には反対です。それは過去のDirectML経路の問題であり、CUDAでも同じ問題が発生すると断定する根拠にはなりません。

ただし、`CUDAExecutionProvider` が利用可能と表示されるだけでは不十分です。CUDAとCPUのノード配置、GPUでの実計算時間、CPUとのベクトル一致を確認します。`gpu_mem_limit=8GB` もCUDA EPのメモリアリーナ設定で、プロセス全体のVRAM上限を保証するものではありません（移植版 `egara_inference.py:34-39`）。<Cite ref="turn220768search0"/>

最初の実測項目は、同じ画像群をCPU/GPUで処理したときの1枚あたり時間、GPU使用率・ピークVRAM、出力ベクトルのコサイン一致、近傍検索順位の一致です。FP32既存ベクトルとの互換性を保ちます。

**バッチ不可も、普遍的な結論にはしません。** 元のONNXでは出力shapeやアスペクト比ごとの入力shapeが制約でした（元リポ `docs/MODEL_SELECTION_2026-08-06.md:551-558,734-738`）。現行モデルで同一shape画像のバッチが可能かを調べ、無理なら1枚ずつGPUで処理すれば十分です。Neon案の「バッチ64〜128、1万枚数分」は実測がないため採用しません。

追加モデルは次の順番が妥当です。

- **EgaraNet単独**：まず個人嗜好に対する予測性能を測る。既存資産が使えるため導入負荷が最小。
- **SigLIP / SigLIP 2**：意味・題材の識別にも強いので、絵柄学習に加えるとタグとの重複が起きやすい。EgaraNetでは失敗した作品に対する改善を確認できた場合だけ追加する。Googleの公開モデルにはApache-2.0のものがあります。<Cite refs={["turn666945search0","turn666945search4"]}/>
- **独立したDINOv3**：初期採用しない。EgaraNet自身がDINOv3のバックボーンを含むため、情報が重複する可能性が高い（元リポ `docs/MODEL_SELECTION_2026-08-06.md:633-661`）。

Neon案にある「EgaraNetの構図1024次元を追加の学習軸にする」点にも、現段階では反対です。元の設計は構図とタグの重複を懸念して、構図を検索用途に分離しています（元リポ同文書`:605-620`）。まず、この判断を覆す実測が必要です。

### 3. 教師信号とコールドスタート

教師信号は**その判定が何を意味しているか**で分けます。

| 信号 | 視覚嗜好への使い方 |
|---|---|
| SuperLike | 強い正例。ただし題材への好意も混ざる |
| Like | 標準の正例 |
| hate(style) | **明示的な絵柄の負例** |
| hate(genre) | 絵柄の負例にはしない |
| Skip | 負例にしない。未確定・気分・既知作品などが混ざる |
| 保存済み・ブクマ済み | 弱い正例。選択バイアスと重複に注意 |
| 閲覧・Opened | 主に「見た」という露出情報。好意の証拠にはしない |

Neon案の `skip=-0.25` を絵柄学習にそのまま用いることには**反対**です。元の仕様でもSkipは軽い見送りであり、明示的な拒否ではありません（移植版 `discovery_ranking.py:22-35`）。

また、現行の `hate(style)` は作者側へ、`hate(genre)` はタグ側へ振り分けられます（移植版 `legacy/database.py:24-31`）。新しい絵柄モデルは、この区別を踏襲するべきです。

学習方法は、判定量に応じて切り替えるのがよさそうです。

**正例しかない初期段階**では、好きな絵柄に近いかを見るだけにします。まず1つの重心を基準にし、明らかに離れた好みの集団が確認できれば2〜4個程度のプロトタイプへ広げます。数は推測上の初期候補であり、固定しません。

**hate(style)が蓄積された段階**で、負例からの距離も利用します。ただし、正例の重心と負例の重心を単純に引くだけだと、嫌いな作風が複数あるときに不安定です。近傍法とプロトタイプ法を比較します。

同じ作品の「保存＋Like＋SuperLike」を3つの独立した正例として数えないことも重要です。評価単位を作品に揃え、連作や同一作者の大量作品が学習全体を支配しないよう重みを調整します。

### 4. 画像のない候補への適用

ここは、今回の設計でいちばん慎重に扱いたいところです。

画像取得前に適用できるのは、基本的に作者ベクトルDです。ただし作者内の作風が安定しているとは限りません。

Dでは、作者の既存画像ベクトルの平均だけでなく、**作品数とばらつき**を信頼度に使います。例えば画像が1枚しかない作者は低信頼、5枚あっても互いに大きく異なれば低信頼にします。必要なら作者内に複数の作風プロトタイプを持ちます。具体的な必要枚数は評価で決める値です。

Aについては、先読みが完了した画像に限って視覚スコアを計算します。現状は画像取得の完了通知が、主に現在カードの再読込用です（移植版 `ui/learning_view.py:1408-1413`）。したがって、画像取得直後の埋め込み処理と、後続候補への安全な順位反映を設計する必要があります。

**表示中のカードをいきなり動かさない**ことを契約にします。既に表示中・操作中の候補や保護対象の先頭カードを固定し、それ以降で利用可能な候補だけを並べ替える方針です。表示後に先読みされた画像が次回の候補補充で役立つ、という控えめな効果から始めます。

サムネイルCは、次のペア比較を実施してから判断します。同じ作品を「保存原画」「学習画面のview画像」「192pxサムネイル」に変換して、埋め込みのコサイン類似度、近傍Top-kの一致率、ランキング相関、実際の判定予測への影響を測ります。平均コサインが高いだけでは不十分で、**好みと嫌いの順位が入れ替わらないか**が重要です。

なおPixivの画像はAPI本体とは別のCDNから配信されますが、「APIと完全に独立したレート制限だから自由に大量取得してよい」とは言えません。これは**未確認の部分**です。

移植版では画像取得も `get_image_bytes()` → `_get("image")` という経路を通ります（`pixiv_read_client.py:799-828,1792-1797`）。Bを将来導入する場合は、CDN取得回数と必要な作品情報API取得回数を両方計上し、取得停止ゲート、認証停止、429停止、全体のリクエスト予算へ従わせます。

第一段階ではBを採用しないため、**視覚学習を有効にしてもPixivへの追加GETは0件**を受入条件にできます。

### 5. 既存順位への統合

順位付けの中心は引き続き現行のメタデータスコアにします。

\[
s_0=0.5\,s_{\mathrm{tag}}+0.5\,s_{\mathrm{author}}
\]

ここでタグはWilson下限、作者はBeta事後平均です（移植版 `discovery_ranking.py:362-402,506-545`）。

視覚学習は独立した補正値を返す設計にします。

\[
s_{\mathrm{final}}
=
\operatorname{clip}\left(
s_0+\alpha\,c\,(v-0.5),\ 0,\ 1
\right)
\]

`v` は検証データで尺度調整した視覚好みスコア、`c` は教師信号数・画像一致度・作者ベクトルの安定性などから決まる信頼度です。`α` は初期には最大0.05〜0.10程度の小さな補正を**仮置き**して比較するのがよいと思います。この数値自体に実測根拠はありません。

重要なのは次の契約です。

**OFF、画像なし、モデル不一致、古い判定世代、GPU失敗の場合は、補正を計算せず元の `rank_candidates` と完全に同じ結果へ戻す。**

視覚スコアは、候補の取得元や検索語を変更せず、既存の3枠の内部順位に限定して使います。枠の比率は確実30%、題材探索50%、絵柄探索20%が既定です（移植版 `discovery_ranking.py:161-165,621-683`）。作者拒否、クォータ、クールダウンは元のまま通します。

絵柄探索枠で「似た好み作品」だけを優遇しすぎると、未知の作風を探す枠の意味が失われます。そのため、**視覚類似度が低い未知作者をすべて排除しない**ことも必要です。

### 6. 評価方法と撤退条件

ここは仮説に明確に反対する点があります。

**「判定履歴を80:20の時系列で分ければ客観評価できる」は、そのままでは成立しません。**

移植版の `learning_repository.py:68-129` では、同じ作品を再判定すると以前の判定を上書きします。Undoでは履歴行を削除し、振り返りからの復元では判定日時が変わります（同`:164-195,217-255`）。

したがって現在の履歴を日時でソートしても、**過去のある時点で実際に何を学習済みだったか**を完全には復元できません。さらに、過去に判定された作品の画像がキャッシュから消えている可能性があります。

私なら評価を2段階に分けます。

**既存データによる予備評価**では、画像または埋め込みが確認できる作品だけで、正例とhate(style)の分離性能を測ります。ただし「画像が残っている作品に偏った結果」であることを明示します。

**本評価**では、今後の表示・判定時に、候補集合、当時の基準スコア、実際に提示した作品、画像特徴、判定、履歴リビジョンを独立ストアへ記録します。その記録を時系列で分割し、各時点で利用可能だった情報だけで予測を再現します。

比較する条件は、現行のみ、現行＋D、現行＋A、現行＋A＋Dです。未知作者・既知作者、タグが似ている作品群、画像欠損群も分けます。

評価指標は目的別に分けます。AUCやPR-AUCは視覚嗜好を予測できる判定ペアがある場合に使い、NDCG@10は実際に評価可能な候補集合に対して使います。表示されなかった作品を勝手に「嫌い」と扱ってはいけません。Top-10のhate(style)混入率や、実際に「好みかも」と感じた件数も見ます。

初期の成功目安としては、**NDCG@10の相対5%以上の改善**を仮の候補にできます。ただしサンプルが少なければ統計的な裏付けは弱いため、差の信頼区間も確認します。これは設計上の提案で、実測で決まった基準ではありません。

撤退条件は明確です。複数の時系列区間で元の順位より悪い、hate(style)の上位混入が増える、未知作者の発掘が悪化する、追加通信が発生する、OFFで元の順番に戻らない――このいずれかが確認されたら補正の適用を止めます。

また「個人利用ではオンラインA/Bができない」という仮説にも反対です。十分なデータ量は課題ですが、本人の同意のうえでセッションを交互に切り替える、あるいは候補をブラインドで二択比較する小規模なオンライン評価は可能です。むしろ、**本人が本当に好む作品に出会えたか**を測るには有効です。

### 7. キャッシュ、再学習、VRAM、設定UI

永続化は別の所有マーカー付きストアにします。候補画像の特徴、モデル識別子、画像内容のSHA-256、画像種別、前処理バージョン、判定リビジョン、学習世代を区別して保存します。元の `learning.sqlite3` と既存の「似た絵を探す」台帳は、視覚学習の削除対象にしません。

キャッシュを無効化すべき契機は、モデル・重み・前処理の変更、画像内容の変更、判定のUndo・再判定・理由変更、保存画像の削除、全リセットです。

特にUndoは重要です。古いGPU処理が後から完了しても、古いモデル結果を復活させないよう、**判定更新の時点で公開スコアを即時失効し、最新世代だけを公開**する設計にします。元リポの学習リセットはseedを維持する仕様なので（移植版 `learning_service.py:362-369`）、判定リセットと視覚学習データの完全削除では何を残すかを区別します。

VRAMは「13GBまで使い切る」と決め打ちしません。初期は同時GPU推論を1ジョブに制限し、Egara類似検索、WDタグ付け、他のGPUアプリが利用中なら視覚学習を後回しにします。バッチを縮小しても余裕がなければ停止し、UIと順位計算は元の経路で動かします。

設定画面は「視覚による好みの補正 ON/OFF」「実行状態」「今すぐ解析」「解析停止」「視覚学習データ削除」の基本操作で足ります。初期評価中は補正をOFFにしてシャドー実行し、効果が確認できてから自動実行の既定値を決めるのが安全です。スケジュールはアイドル時・手動・設定による定期実行とし、常駐GPUモデルは不要です。

### 8. フェーズ1〜3とRelease前の規模

| フェーズ | 追加するもの | 出口条件 |
|---|---|---|
| **1：測る** | EgaraNet GPU検証、既存画像の埋め込み再利用、教師データの対応付け、シャドー評価 | CPU/GPU互換確認、画像カバー率と推論時間の実測、好み予測で元方式との比較が可能 |
| **2：小さく効かせる** | A＋Dの補助スコア、独立キャッシュ、Undo追従、OFF復帰、設定UI | 元機能・検索・通信が不変、OFFの順位完全一致、視覚学習の有効性が基準を満たす |
| **3：必要なら拡張** | 多プロトタイプ、追加モデルの比較、任意の候補プール画像取得など | 追加方式ごとに、精度改善が導入負荷・通信増加を上回ると実測で示せる |

私の判断では、**フェーズ1と、小さく絞ったフェーズ2はRelease前の追加機能として検討可能な規模**です。ただし実装・テスト・受入を終えるまで、Release可能とは断定できません。

フェーズ3は、Release前の必須条件にしない方がよいです。Neon案をそのまま導入すると、モデル配布、GPUランタイム、複数スコアの調整、画像取得、学習・推論・UI更新の競合まで一気に増えます。

本人が効果を体感する仕掛けとしては、候補ごとに**「絵柄が近い保存作品3枚」**を見せる案に賛成です。ただし「この3枚があるから必ず好き」と断定せず、実際の近傍作品と近さを表示します。

もう一つ、同じ候補集合を「元の順位」と「視覚補正ありの順位」で並べ、どちらが好みに近いかを名前を伏せて選ぶ比較画面を勧めます。これは数値評価と本人の感覚を結び付けるのに役立ちます。

### 9. 見落としやすいリスク

最も大きいリスクは、GPUの計算能力よりも**学習データの意味と入手可能性**です。とくに以下は実装前に検証したい点です。

**ライセンス**：EgaraNetのモデルカードはApache-2.0ですが、内部のDINOv3にはMeta独自のライセンスがあります。Releaseでモデルを同梱・再配布する場合は、派生モデルの権利関係と同梱条件を確認する必要があります。<Cite refs={["turn220768search3","turn666945search6"]}/>

**モデル配布とオフライン起動**：外部アクセスなしでも通常起動できる設計にします。モデルはユーザーが導入したローカルファイルをハッシュ検証し、追加のモデルダウンロードを起動処理に組み込まない方がよいです。

**Windows依存**：Python 3.13、ONNX Runtime GPU、CUDA、cuDNNの組み合わせは隔離環境で固定して動作確認します。PyTorchを導入する場合も、モデルをロードするだけのために巨大な依存を本体へ持ち込む価値があるかを測ります。<Cite refs={["turn220768search0","turn666945search2"]}/>

**作者の作風変化**：作者ベクトルDを1つの平均に潰すと、過去の好み絵柄から変化した新作を過小評価する可能性があります。作者平均が安定するかを、作者内の作品間距離で確認します。

**画像種別・ページ差**：うごイラ、複数ページ、サムネイルへのフォールバック、長辺512pxへの縮小によって、入力画像の特徴が変わります。どのページのどの画像から作ったベクトルなのかを必ず識別します。

**テストの容易性**：リポジトリの単体テストでは合成ベクトルで順位契約を確認できますが、それだけでは実際の絵柄学習の有効性を示せません。性能評価には隔離した実画像特徴と判定結果が必要です。

なお元リポのM-3は依然として未実装であり、M-1の走査とM-4の類似検索だけが実装済みであることを確認しました（元リポ `docs/archive/DISCOVERY_WORK_QUEUE_2026-08-07.md:3655-3666`、`tools/scan_style_embeddings.py:431-479`、`library_tab.py:944-1165`）。今回の調査では**実GPU推論、実Pixiv通信、実装・ファイル変更は行っていません**。

### おにぃに確認したいこと（5つ）

1. **保存済みの画像は実際に何作品・何ページありますか？** そのうちEgaraNetの埋め込みが既にあるのは何件でしょうか。
2. **判定は何件ほどありますか？** とくにSuperLike、Like、hate(style)の件数と、その画像がローカルに残っている割合を知りたいです。
3. **一番改善したいのはどちらですか？** 「既に好きな作者の中で好み作品を当てる」か、「まだ知らない作者・絵柄を発掘する」か。ここでAとDの優先順位が変わります。
4. **GPU処理の許容範囲は？** 初回一括解析に数時間かかってもよいか、普段の利用中にも動かすか、ゲームやほかのGPUアプリの利用中は完全停止するか。
5. **視覚学習のための追加画像取得は将来許容しますか？** 初期設計は0件増で進めますが、効果が実証された後に限り、明示的な上限付きでBを試す余地を残すかどうかです。

> まず移植版と元リポの実装・設計書を照合して、実装済みの経路と未実装の構想を切り分けます。そのうえで RTX 5080 の推論環境、モデルのライセンス、評価方法を外部資料でも確認し、Release 前に試す価値のある最小構成まで絞ります。今回は読み取りと設計検討だけにします。

> 現時点で重要な点が一つ確認できました。移植版の `egara_inference.py` には、すでに CUDA を選ぶ経路があります。ただし、その経路で RTX 5080 の実推論が成功した証拠はまだ確認できていません。まずここを使えるか評価するのが自然です。

> 評価方法について、かなり大きな落とし穴が見つかりました。移植版の判定履歴は、同じ作品を再判定すると古い判定を上書きし、Undo では履歴行を削除します。したがって、現在の履歴を日時順に80:20で分けるだけでは、過去の学習状態を正確に再現できません。
